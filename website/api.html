授权模型

能力开得越多，
越不能让你失去控制权。

把口子开大很容易，难的是开大之后你还看得住。所以每一项高危能力都同时受这四条约束—— 它们不是加分项，是能力开放的前提。

01

默认全部禁用

插件必须在 plugin.json 里明确声明要用哪几项能力，再由你在「插件管理」里逐项打开。没声明的、没授权的，调用一律被拒——不是提示，是真的拿不到。

02

用的时候你看得见

只要有插件正在用摄像头、麦克风或屏幕，托盘就常驻显示「谁正在用什么」，旁边一个「停止」可以立刻掐断。授权那一刻的同意，不等于此后每一刻都被蒙在鼓里。

03

事后查得到

高危能力的每次调用都写进审计日志，在插件详情页可以直接翻。哪个插件、什么时候、用了什么——不用你去猜。

04

拿不到的东西就是拿不到

文件访问只能落在你亲自选中的目录里，且每次操作都重新校验路径；托管的 ffmpeg / adb 只能按名字调用，插件拿不到可执行文件的真实路径。

无需授权

装上就能用的部分。

这些能力不碰你的文件、设备和其它程序，所以不需要单独授权，插件写了就能调。 大部分工具类插件到这里就够用了。

边界

做不到的，也一并写清楚。

能力清单容易写得漂亮，真正有用的是知道它在什么情况下不工作。下面每一条都是真机验收里实际撞到过的。

  • 锁屏时，屏幕与输入相关能力一律失败。 截屏、录屏、取色、鼠标移动、弹系统对话框在锁屏后全部拿不到句柄——这是 Windows 的会话隔离，不是 iTools 的限制。 后台常驻插件必须处理这类失败，不能假设屏幕随时可用。
  • 模拟输入要求目标是前台窗口。 而且对以管理员权限运行的窗口无效（Windows UIPI 拦截），普通权限的程序碰不到高权限程序。
  • 执行外部程序不经过 shell。 参数逐个传给目标程序，所以 &、|、> 这些 shell 符号不会生效——要管道请自己起 cmd /c。
  • 文件访问不能靠猜路径。 插件写一个绝对路径进去是没用的，必须由你在对话框里亲自选中；而且每次读写都会重新解析真实路径，防止授权后被替换成软链接绕过。
  • 托管运行时必须先下载。 ffmpeg 约 160 MB，首次使用需要 runtime.ensure 下载并校验哈希；校验不通过绝不落盘，宁可装不上也不放行来路不明的可执行文件。
  • 摄像头录像不由 iTools 直接提供。 要录摄像头请用 camera.streamStart 取帧后交给托管的 ffmpeg——record.videoStart 走的正是这条路。
