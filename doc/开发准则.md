# iTools 开发准则

> 本准则的第一目标：**杜绝夸大功能与虚假实现**。任何人（包括 AI 助手）参与 iTools 开发，都必须遵守；每次功能完成、每次发布前，都要按本准则的「审查清单」核对。

---

## 一、诚信实现准则（红线，不得违反）

1. **真实实现优先**
   每个声称存在的功能，必须有真实、可运行的实现。**禁止**用空桩、写死的假返回、硬编码假数据来「冒充」已实现。命令不能只注册不干活。

2. **UI 与实现必须一致（不夸大）**
   界面上的每一个按钮、开关、输入框、菜单项、文案，其行为必须与后端实际能力一致。**禁止**出现「看起来能用、点了却不生效」的控件（例如：能打开、能保存，但后端根本不读取这个值）。

3. **未完成必须对用户诚实标注**
   占位 / 桩 / 演示 / 仅本地 / 未接后端 的功能，必须在 **UI 上明确告知用户**（如「敬请期待」「演示」「本地资料」「未生效」），或直接禁用 / 隐藏。**不得**让用户误以为可用。「敬请期待」式占位是诚实的；「假装能用」是欺骗。

4. **新增命令必须四处闭环**
   新增 Tauri 命令，必须同时满足：① 有真实 `#[tauri::command]` 实现（非空桩）；② 在 `lib.rs` 的 `generate_handler!` 注册；③ 在 `build.rs` 的 `COMMANDS` 白名单；④ 前端 `invoke` 的命令名 / 参数 / 返回字段与后端精确一致。缺任何一环都算未完成。

5. **前后端接口一致（防幻觉）**
   前端 `invoke("命令名", {参数})` 与后端函数名 / 参数名必须对得上；返回结构体字段（含 `serde(rename_all)` 后的实际名）与前端 interface 及所有字段访问必须一致。**禁止**臆造不存在的命令、参数或字段。

6. **不谎报，如实汇报**
   交付或汇报时，必须如实区分：哪些是**真实现**、哪些是**桩 / 占位**、哪些**未验证**。测试失败、步骤跳过、仅编译未真机验证，都要明说。**禁止**把「写了代码」说成「功能可用」。

7. **联网类功能特别约束**
   账户、登录、数据同步、云、代理等「看起来要联网」的功能，在**真正接入后端之前**，必须在 UI 标注真实状态（如「本地资料（未接入云账号）」「代理未生效」），**禁止**用本地桩伪装成联网能力。措辞上避免「注销账号」「云同步」等暗示服务端却不兑现的词。

8. **安全与隐私红线**（详见 README「开发约定」）
   - 不硬编码个人 / 敏感数据（昵称、路径、邮箱等）；账号类默认值必须为空。
   - 凭据（token / 密钥 / 密码）只从**环境变量**读取，源码与二进制零明文。
   - 服务端地址 / 域名 / endpoint 必须可配置，不写死进代码。
   - **运行日志：可以有，但不得含敏感内容。**

     > **本条 2026-08-18 修订**，原文是「Release 版不产调试日志」。改的是形式，不是精神——
     > 这条红线的初衷从来是**隐私与安全**（别把用户的东西留在他磁盘上、别泄露内部细节），
     > 而不是「日志本身有罪」。按原文的字面执行，代价很具体：release 是 GUI 子系统
     > （`windows_subsystem = "windows"`），进程没有控制台、stderr 是黑洞，于是
     > 「已有同类实例在运行，本进程退出」「MCP 默认端口被占已改用 7346」这类**唯一能解释
     > 用户所见怪象**的信息在用户机器上根本不存在。用户报「双击图标没反应」，我们和他都拿不出
     > 任何证据。所以现在两种构建都落文件，红线改为约束**内容**。

     - **位置固定、两种构建互不覆盖**：release → `%LOCALAPPDATA%\itools\itools.log`；
       debug → exe 同目录（`target\debug\itools.log`）。实现见 `src-tauri/src/logging.rs`。
     - **必须有上限**：单文件 2 MiB，超了轮转成 `itools.log.1`，**只留一代**。
       常驻托盘进程能连着跑几周，日志不许无限长，也不许在用户盘上越攒越多。
     - **判据只有一条**：这一行**原样贴进工单 / 发到群里，用户会不会介意**？
       日志的定位是**运行诊断**（谁启动了、端口换没换、哪一步失败了），不是用户行为审计。
     - **硬要求，按三类分**（`src-tauri/src/logging.rs` 模块头「隐私」一节是同一份口径的
       落地版，改动其一务必同步另一处）：
       - **用户内容一律不入日志**：凭据（token / 密码 / Cookie / API key）、账号与手机号 /
         邮箱 / 昵称、剪贴板、搜索框里敲的原文、文件与消息正文（含插件 `itools.notify` 的正文），
         以及插件经 `window.itools` 传进来的任意字符串。**只记「谁 + 多长 + 什么错」**。
       - **用户自选的路径只记末段**：文件 / 目录对话框选出来的路径，只留扩展名或末级目录名——
         完整路径带着 Windows 用户名和私人目录结构，文件名本身往往就是隐私。
       - **应用自有路径可以照打**：`%LOCALAPPDATA%\itools\...`、插件根、暂存区这类结构固定的
         自有路径照常记全——排查安装 / 播种 / 回滚就得知道具体是哪个目录，抹掉等于把可观测性清零。
       - **凭据在任何形态下都得抹成 `***`**（`ProxySpec::display()` 是既有的正确示范）：
         不只是「不主动打」，还包括拼在 URL、错误串、`{:?}` 调试输出里被顺带带出来的那些。
     - ⚠ **别走另一个极端**：脱敏是把**用户内容换成可诊断的元信息**，不是把整行删掉。
       release 之所以加文件日志，就是为了「用户说没反应」时有据可查；删空了等于白加。

## 二、发布前审查清单（每次功能完成 / 发布前逐项核对）

- [ ] 每个 UI 控件都能追到**真实生效**的后端实现（UI → invoke → 命令实现 全链路走通）？
- [ ] 有没有「存了不生效」的开关 / 按钮 / 输入（改了没有任何实际效果）？
- [ ] 所有占位 / 桩 / 仅本地 功能，都已在 UI **明确标注**，不会误导用户？
- [ ] 新增命令是否 **实现 + `lib.rs` 注册 + `build.rs` 白名单 + 前端调用** 四处闭环？
- [ ] 前后端命令名 / 参数 / 返回字段是否**逐一对得上**（无幻觉、无拼写漂移）？
- [ ] 改过跨 `invoke` 边界的结构体后，是否重跑 `cargo test -j1 contract_field_names_frozen` 重新生成契约清单，并跑 `npm run check:contract` 双向校验通过？（`invoke<T>()` 只是类型断言，`cargo test` 与 `tsc` 双绿也发现不了字段错位——这道闸门是唯一能发现它的地方；注意它当前只纳管了部分结构，未纳管的仍需人工核对）
- [ ] 有没有**硬编码假数据**冒充真实结果？
- [ ] 联网类功能是否**如实反映**「已接入 / 未接入」？
- [ ] 是否有硬编码的个人数据 / 本机路径 / 明文凭据 / 写死的服务端地址？
- [ ] 本次新增 / 改动的 `ilog!` 是否**都不含用户内容**？（凭据、账号 / 手机号 / 昵称、剪贴板、用户敲的搜索词、文件与消息正文、插件传进来的任意字符串；用户自选路径是否只留了末段——逐条对第一节第 8 条那份三类口径过。release 日志长期躺在用户磁盘上、报障时整份发出来，漏一行就是漏给所有用户）
- [ ] `cargo test` / `cargo clippy`（0 warning）/ 前端 `tsc` 是否通过？关键功能是否**真机验证**过？
- [ ] 汇报是否如实分清了「真实现 / 桩 / 未验证」？

## 三、审查机制（怎么执行）

**何时审**：每次功能实现完成后、以及每次发布前，必须执行一次。

**怎么审**：
- **追全链路**：从用户能看到的 UI 入口，一路追到后端实现体，确认真实生效——不要凭 UI 外观或命令名就判定「已实现」。
- **对抗性视角**：默认怀疑「这个功能是不是假的 / 夸大的」，主动去找空桩、假返回、不生效的控件、对不上的接口。有条件时用**多个独立视角**分别审再交叉验证（例如按功能模块并行审查 + 对抗验证），减少单一视角的盲点。
- **四档判定**：对每个功能给出结论——
  - `真实`：有真实现、确实生效；
  - `诚实占位`：未完成但已如实标注（可接受）；
  - `欺骗性桩`：UI 像能用、实际不生效且未告知用户（**必须修**）；
  - `虚假`：声称有、后端根本没有或返回假数据（**必须修**）。
- 判为「欺骗性桩」或「虚假」的，发布前必须修复：要么补全真实现，要么如实标注 / 禁用 / 移除。
- **结论本身必须可复现**：以「实测」为由下的技术结论（尤其是「某能力做不了 / 某依赖有毒」这类**要砍功能**的结论），必须先确认 A/B 两侧**只差你以为的那一个变量**。基于错误证据做出的「诚实降级」（砍功能 + 改文档 + 改 UI）同样是把用户带偏——真实案例见第四节 4.1。

**记录**：审查结论（尤其欺骗性 / 虚假项）应向需求方如实呈现，不得隐瞒或美化。

## 四、踩坑档案（写下来是为了不再错第二次）

### 4.1 Windows 上 lib 单测 exe「启动即退」（`0xC0000139`）——**先查清单，再怀疑依赖**

> 这个坑已经**让两轮技术判断出错**（第二轮是在第一轮的错误结论上继续加码），所以单独立档。

**现象**：`cargo test -j1 --lib` 编译、链接全部通过，但产出的**测试可执行文件一启动就退**，退出码 `0xC0000139`（`STATUS_ENTRYPOINT_NOT_FOUND`），一个测试都没跑起来（输出看上去像「测试全挂」）。同一份源码的 **bin 目标**（应用本体、`--bin` 的单测 exe）却一切正常。

**真因**（2026-08-12 实测定位，非推理）：

1. lib 单测 exe 导入了 `comctl32!TaskDialogIndirect`——由依赖 `rfd`（原生文件对话框）引入；
2. `C:\Windows\System32\comctl32.dll` 是 **v5.82**，`dumpbin /exports` 里 `TaskDialog*` 的条目数是 **0**：它**根本不导出**这个函数；
3. 该函数只存在于 WinSxS 中的 **comctl32 v6**，而 v6 必须由**应用清单**（`Microsoft.Windows.Common-Controls` **6.0.0.0**）激活才会被加载；
4. `tauri-build` 生成的 `resource.lib`（图标 + 版本信息 + **清单**）是通过 `cargo:rustc-link-arg-bins` 发出的——**只作用于 bin 以及 bin 的单测 exe，lib 的单测 exe 一份清单都拿不到** → 进程加载期解析导入表即失败。

**当前状态：已持久修复**（`src-tauri/build.rs::emit_app_manifest`）。做法是把清单从 tauri 手里接管过来——`tauri_build::WindowsAttributes::new_without_app_manifest()` 让 tauri 只发图标与版本信息，再由 `embed_resource::compile_for_everything` 用**不带后缀**的 `cargo:rustc-link-arg` 发同一份清单（源文件 `src-tauri/windows-app-manifest.xml`，内容与 tauri-build 的默认清单逐项一致），于是 **bin / bin 单测 / lib 单测 / cdylib 全都拿得到**，且因 tauri 不再发，不会重复链接。编不出资源就让构建失败（`.manifest_required()`），绝不静默产出跑不起来的二进制。

> ⚠️ 改 `windows-app-manifest.xml` 等于改**正式发布产物**的清单，不是只影响测试。加 DPI 感知 / UAC / longPathAware 任何一项都要真机验证后再合入。

**当时的取证手段（诊断同类问题仍然照用）**：把下面这份清单塞进那个 lib 单测 exe，再跑一次就全绿。

```xml
<?xml version="1.0" encoding="UTF-8" standalone="yes"?>
<assembly xmlns="urn:schemas-microsoft-com:asm.v1" manifestVersion="1.0">
  <dependency><dependentAssembly><assemblyIdentity type="win32"
    name="Microsoft.Windows.Common-Controls" version="6.0.0.0" processorArchitecture="amd64"
    publicKeyToken="6595b64144ccf1df" language="*" /></dependentAssembly></dependency>
</assembly>
```

```
mt.exe -manifest common-controls6.manifest -outputresource:<lib单测exe完整路径>;#1
```

**实测对照（四组，结论一致：变量是清单，不是依赖）**：

| 组合 | 结果 |
|---|---|
| 依赖树**无** socks（`cargo tree -i socks` 查无此包）+ 原始 lib 单测 exe | ❌ 启动即退 `0xC0000139` |
| 无 socks + 用 `mt.exe` 给该 exe 塞一份 Common-Controls 6.0.0.0 清单 | ✅ 119 passed |
| **有** socks（`ureq features = ["json", "socks-proxy"]`）+ **bin** 单测 exe（tauri-build 自带清单） | ✅ 正常加载运行 |
| **有** socks + lib 单测 exe 塞清单 | ✅ 119 passed |

**教训与判据**：

1. **它与增删任何依赖都无关**——但**增删依赖会顺带重新链接测试二进制**，于是「改了依赖就崩 / 去掉就好」看起来像因果，实际只是「这一次有没有重链、复用的旧 exe 恰好有没有清单」。**上一轮据此把锅扣给了 ureq 的 `socks-proxy` feature**，并基于这个错误证据做了一整轮「诚实降级」：禁用该 feature、在 `http::normalize_proxy` 入口拒绝 `socks*://`、文档与设置页全部改写成「不支持 SOCKS」。证据一错，「诚实」也会诚实地把用户带偏——**诚信红线要求的不只是如实汇报结论，还包括结论本身经得起复现**（见第三节末条）。
2. **判据：测试二进制启动即崩，先查清单、再怀疑依赖。** 三步定位——① `dumpbin /imports <exe>` 看它到底导入了哪个 DLL 的哪个函数；② `dumpbin /exports C:\Windows\System32\<该 DLL>` 确认系统里的那份导不导出这个符号；③ 用 `mt.exe` 塞清单后重跑。三步都不用改一行业务代码。
3. **要判断「某依赖 / 某 feature 是否有问题」，用拿得到清单的目标去测。** 本项目修复前，lib 单测 exe **天生没有清单**，它这种崩溃是**背景噪音**、与被测依赖无关；当时正确的做法是改用 **bin 单测**（`cargo test --bin …`，tauri-build 的清单覆盖得到）复核。修复后（4.1 上文）lib 单测同样带清单，两者都可用——但换到别的仓库、或哪天有人把 `build.rs` 里那段清单逻辑删掉，这条判据依然成立。
4. **A/B 对照必须控制「是否重新链接」这个变量。** 只改 `Cargo.toml` 再各跑一次 `cargo test`，两边的测试 exe 可能一个是新链的、一个是缓存复用的——那不是 A/B。必要时比对二进制的 metadata 哈希 / mtime 确认它真的被重链过。
5. **修法只有「接管清单」这一条，别再试这两条死路**：① `cargo:rustc-link-arg-tests` 会报「does not have a test target」——它只覆盖 `tests/` 目录的集成测试，不含 lib 单测，cargo 也没有「只给 lib 单测」的粒度；② **保留** tauri 那份清单、再额外用不带后缀的 `cargo:rustc-link-arg` 补发，会让 bin 与 bin 单测重复链接同一类资源 → `CVT1100 资源重复` / `LNK1123`。正确解法是让 tauri **不要**发（`new_without_app_manifest()`），改由 `build.rs` 一处发给所有目标——即当前实现。

### 4.2 编译期 `0xc0000005`：清增量缓存重试

本项目多个 agent / 会话共用同一个 `target/` 时，`cargo` 偶发在**编译期**（不是运行期）以 `0xc0000005` 退出。已知与业务代码无关，删掉 `src-tauri/target/debug/incremental` 后重试即可。跑 cargo 一律加 `-j1`。
