# iTools 插件开发者中心 v1

> 面向 **插件开发者**：本文说明「正在开发的插件怎么在一个与正式环境**物理隔离**的沙盒里跑、调、看数据、试权限、测同步失败分支」。
> 插件怎么写见 [`插件开发规范.md`](插件开发规范.md)；写完怎么发出去见 [`插件分发规范.md`](插件分发规范.md)；本文管 **调试** 与 **提审上架**（第 4.6 节）这两段。
> 本文所述能力**均以客户端已实现的行为为准**。第七节是诚实清单——凡写「抓不到 / 不支持」的，就是真的没有，不要按能用去设计调试流程。

入口：**管理中心 → 左侧导航「开发者中心」**（在「插件管理」下面一项）。

## 一、为什么要单开一个调试环境

在开发者中心之前，调试一个还没写完的插件只有一条路：把它扔进正式的 `plugins/` 目录，然后当正式插件用。这条路有三个**真实**的坑，而且都不是「体验不好」级别的，是「会污染正式数据 / 会把垃圾推上云 / 根本无从排查」级别的：

**坑一：半成品插件会挤进主搜索。**
`plugins/` 下的插件一被扫到就参与主搜索索引展开（`expand_commands`）。你的 `debug-test` 插件如果声明了 `{"type":"text"}` 触发，它会对**任意非空输入**都出现在搜索结果里；写错一个 regex（比如 `.*`）更是每敲一个字都命中。开发期的插件本来就该只有你自己能看见，不该和你日常在用的插件抢结果列表。

**坑二：`itools.data.*` 写的是正式库，而且 `sync_now` 会真的把它推上云。**
两套存储的行为完全不同，很多人到出事才发现：

- `itools.db.*` → `plugin_db_*` → `Db::pkv_*`，写正式库的 `plugin_kv` 表，**纯本地、不同步**；
- `itools.data.*` → `plugin_data_*` → `sync::DataStore` → `Db::pd_*`，写正式库的 `plugin_data` 表，**参与云同步**。

关键在于同步的粒度：`DataStore` 的全量同步会先 `db.pd_namespaces()` 取出「所有有数据的命名空间」，然后**逐个上推**。它不认识哪个命名空间是「正式插件的真数据」、哪个是「你调试时随手写的 `test123`」——只要落在同一个库里，就一视同仁地推到服务端。于是「本机调一调」变成了「往自己的云账号里灌垃圾」，而且删起来很麻烦。

**坑三：插件页出错，UI 上什么都看不见。**
插件页是一个独立 WebviewWindow，没有开发者工具入口时，页面里的 `console.error`、未捕获异常、`Promise` 拒绝**全部沉默**。`itools.xxx()` 调用被后端拒绝（未授权 / 参数不对 / 路径越界）时，reject 的原因也只在插件自己的 `catch` 里——插件没写 `catch` 就等于什么都没发生。表现出来就是「点了没反应」，而你完全不知道是没绑事件、还是 invoke 报错、还是权限被拒。

开发者中心把这三件事一次性解决：**独立加载源 + 独立存储 + 全链路探针**。

## 二、两种加载方式

开发者中心的插件**不来自** `plugins/`，来自下面两处（两者可同时用，一起列在页面顶部的「调试目录（加载源）」列表里）：

### 2.1 固定目录 `dev-plugins/`

一个固定的、不可移除的调试目录，按下面的顺序解析（面板上会显示**真实绝对路径**，一切以面板为准）：

1. 环境变量 `ITOOLS_DEV_PLUGINS_DIR`（测试 / 特殊布局用）；
2. **开发运行**（`tauri dev`）：从 exe 上溯到含 `src-tauri` 的项目根，用它的 `dev-plugins/`；
3. **打包运行**：`%LOCALAPPDATA%\itools\dev-plugins`。

它与正式插件根**永不重合**——否则调试插件会被正式环境一并加载，隔离就白做了。**零构建插件直接放这里**——和正式插件一样是「一个目录 + `plugin.json` + `index.html`」，放进去点「重新扫描」就能跑。

**这个目录由 iTools 在启动时自动创建**（`DevRuntime::new` 无条件 `create_dir_all`），你不用手动建；万一它在运行中被删掉，面板只打一个「目录不存在」标记、不渲染成故障，重启或自己建回来即可。

> ⚠️ **`tauri dev` 会在仓库根多出一个 `dev-plugins/`**（解析规则第 2 条）。它装的是半成品调试插件，**不该进仓库**——本仓库的 `.gitignore` 已经忽略 `/dev-plugins/`（与既有的 `/plugins/` 同理）。在别的项目布局下自建调试目录时，请照样加进 `.gitignore`。

> 还没有插件骨架？在 Claude Code 里用 `/itools-plugin-dev` 让 AI 直接生成一个可运行的插件目录，放进这里即可。

### 2.2 添加调试目录

点「添加目录」选一个**任意本地目录**。它的用途是**指向构建产物**——如果你的插件是 TS / 打包型的，源码目录里没有可运行的 `index.html`，能跑的是构建输出目录。把那个输出目录加进来，改完代码 `npm run build`，回面板点「重新扫描」即可，不用每次往 `dev-plugins/` 拷一遍。

> 本仓库的 `plugin-src/deskbox/`（React + Vite）就是这类插件，不过它现在的 `vite.config.ts` 把 `outDir` **直接指向了正式的 `plugins/deskbox`**——也就是说，开发期每 build 一次都在往正式插件根里写。要用开发者中心调它，请在开发期把 `outDir` 改指到一个调试目录（如 `dev-plugins/deskbox`，或任意目录再用「添加目录」指过去），发版前再改回去。

**每个调试根支持两种形态，自动判别**（这条不搞清楚会白折腾）：

| 形态 | 判别条件 | 典型用法 |
|---|---|---|
| **目录本身就是一个插件** | 该目录下**直接有** `plugin.json` | 把 `plugin-src/xxx/dist` 这类构建产物目录加进来 |
| **目录是插件的容器** | 该目录下**没有** `plugin.json` | 固定的 `dev-plugins/`：扫它的**一级子目录**，每个含 `plugin.json` 的算一个插件 |

容器形态下，`.` 开头的目录与 `node_modules` 会被跳过；子目录里没有 `plugin.json` 的直接忽略（不报错，避免噪音）。

另外三点：

- 目录不存在时面板打「目录不存在」标记、本次扫描跳过它，**不当故障处理**。
- 同一个目录被添加两次（或与固定根重复）只扫一次，不会凭空多出一份「id 冲突」。
- 目录列表持久化，重启还在。固定目录不可移除；手动添加的可随时移除——**只是不再扫描，不会删你的文件**。

### 2.3 ⚠️ 调试环境里 `id` 与 `name` 是两个东西

正式环境强制 `plugin.json.name` == 目录名，所以两者永远相等，可以混着说。**调试环境放宽了这条**（见 5.1），于是它们可能不相等，而分工是明确的：

- **`id` = 目录名。** 调试环境内的唯一标识：**协议 URL、调试库的存储命名空间（`plugin:<id>`）、沙盒目录、日志归属，全都用 `id`**。
- **`name`** —— 只是 `plugin.json` 里写的那个字符串，面板照实显示、拿它报 issue，仅此而已。

结论有三条，都很实际：

1. 你在存储 tab 里看到的数据是**按 `id`（目录名）归的**。改 `plugin.json` 的 `name` 不会让数据搬家；**改目录名会**——改完之后原来那份调试数据就找不到了（还在库里，只是挂在旧 id 下）。
2. 两个调试目录里出现**同名目录**时不会静默取其一：**先扫到的胜出**（保留可运行，并给一条 warn 告诉你冲突对象在哪），**后来的判 `error` 且 `runnable = false`**，两边的路径都在 UI 上看得到。
3. `name` 与目录名不相等时会报一条 warn。**发布前必须让它们相等**，否则正式环境根本不加载（见 5.1）。

## 三、隔离矩阵：调试环境到底隔离了什么

这是本功能的核心。逐行读一遍，特别是「存储」那几行：

| 维度 | 正式环境 | 开发者中心（dev） |
|---|---|---|
| 插件目录 | 单一插件根（打包版 `%LOCALAPPDATA%\itools\plugins`） | `dev-plugins/` + 你添加的任意目录，**多根** |
| 自定义协议 | `itplugin://`（`http://itplugin.localhost/<id>/…`） | **`itplugindev://`**（`http://itplugindev.localhost/<id>/…`），按「id → 目录」映射表解析，不是拼单一根 |
| 窗口 label | `plugin` | **`plugin-dev`**（独立窗口，可与正式插件窗口**同时开着**） |
| 命令白名单 | `capabilities/plugin.json` | `capabilities/plugin-dev.json`：与正式窗**授予同一组 `plugin_*` 能力**（保证「调试里能跑的，装上去也能跑」），只额外多一个 `dev_log_push`（探针上报）。开发者中心的 `dev_*` 配置类命令**一概不给**被调试的插件 |
| KV 存储 `itools.db.*` | 正式库 `itools.db` 的 `plugin_kv` 表 | **独立 SQLite 文件**的 `plugin_kv` 表 |
| 同步数据 `itools.data.*` | 正式库 `itools.db` 的 `plugin_data` 表 | **独立 SQLite 文件**的 `plugin_data` 表（命名空间**同样是 `plugin:<id>`**——隔离靠「另一个库文件」，不靠改名字，这样插件代码两边行为完全一致） |
| 沙盒文件 `readFile/writeFile/removeFile` | `%LOCALAPPDATA%\itools\plugin-data\<id>\files\` | `%LOCALAPPDATA%\itools\dev\plugin-data\<id>\files\` |
| 权限授权 | `AppSettings.plugin_permissions` | **独立的 `dev_plugin_permissions` 表**，两边互不影响 |
| 云同步 `itools.data.sync()` | 真实请求同步服务端 | **本地 Mock**，绝不发出任何网络请求 |
| 账号态 `itools.account.state()` | 本机真实登录态 | **由同步 Mock 的模式推导**（见 3.1） |
| 插件设置 `itools.settings.*` | schema 默认 **+ 用户在管理中心配置的值** | **只有调试插件目录里 `settings.json` 的 schema 默认值**（不读正式插件的用户值） |
| 主搜索 | 参与 | **默认不参与**（可在面板里开开关，见 3.3） |
| 其余能力 | — | **完全一致，不做任何分流** |

调试库与 dev 沙盒的**真实路径直接显示在面板上**（后端返回的 `dbPath` / `filesRoot`），可以点开看、可以直接删——删掉整个 dev 数据目录不会影响任何正式数据。调试库默认落在 `%LOCALAPPDATA%\itools\dev\plugin_data_dev.sqlite`。

> 会话是**按窗口**判定的，不是全局一个「当前插件」。所以正式插件窗和调试插件窗同时开着也不会串味——每个窗口各自知道自己是不是 dev。

### 3.1 哪些分流、哪些不分流

分流的就是上表里点名的那几类：**存储 / 沙盒文件 / 权限 / 同步 / 账号态 / 插件设置**。除此之外，**剪贴板、截图、区域截图、贴图、OCR、通知、热键、录音、录屏、`runCommand`、`itools.fetch`……一律走和正式插件完全相同的实现**。

这是刻意的：调试环境的价值在于「跑起来和正式一模一样，只是数据不脏」。如果连截图都换成假的，那调出来的结论对正式环境就没有参考价值了。代价是：**dev 插件调用真实系统能力时的副作用是真的**——`itools.copyText()` 真的会改你的剪贴板，授权了 `runCommand` 就真的会起进程，授权了 `network` 就真的会联网。

**账号态为什么也要跟着 Mock 走**：`itools.account.state()` 在调试会话里由「同步 Mock」的模式推导（模式不是 `notLoggedIn` 就报已登录）。否则你把 Mock 设成「同步成功」，插件却因为你本机真实账号没登录而**根本不进同步分支**，模拟器就形同虚设。调试环境全程不读真实登录态、不联网。

**插件设置为什么只给默认值**：开发者中心没有设置 tab，没有地方让你覆盖值；后端于是只读调试插件目录里 `settings.json` 的 **schema 默认值**，不去碰正式插件那份用户配置。所以调试期 `itools.settings.get(k)` 拿到的**永远是默认值**——要测「用户改过设置」的分支，请临时改 `settings.json` 里的 `default`。这是本轮的已知限制，见第七节。

### 3.2 为什么「调试数据永不上云」是物理保证

因为 dev 用的是**另一个 SQLite 文件**，不是同一个库里的另一个命名空间。

正式环境的全量同步靠 `db.pd_namespaces()` 遍历「本库里所有有数据的命名空间」。这个 `db` 是正式库的连接，它**根本看不到** dev 那个文件里的任何一行——不需要在同步逻辑里加一句「跳过 dev 命名空间」的过滤，也就不存在「过滤条件写漏了 / 被后续重构删掉」的风险。

这是本设计里唯一一条**结构性**保证，其它隔离项（权限表、沙盒根、账号态、设置）都是「按会话的 dev 标志分流」的逻辑保证。

同理，`itools.data.sync()` 在调试会话里**根本不进入** `DataStore::sync_gated`——不是「进去了但被拦下」，是压根没走那条路。

### 3.3 主搜索开关

面板上叫「**调试插件参与主搜索**」，默认 **关**：dev 插件不进主搜索索引，你在主搜索框里搜不到它们，正常情况下**只能从「运行」tab 启动**。

> ⚠️ **热键是唯一的例外**：调试插件在会话里用 `itools.registerHotkey()` 注册的**全局热键照常生效**，与本开关无关——按下它会唤起（窗口已关就重开）**调试窗口**并派发 `onHotkey`，`info.query` 是 `__hotkey__`。而且这类热键**只登记在进程内**：关掉调试窗口、在「插件管理」里停用插件都**不会**注销它，只有插件自己调 `itools.unregisterHotkey()` 或**重启 iTools** 才会释放。所以「关了开关就一定进不去」的说法是不准确的——一个注册过热键的调试插件仍然可能被你自己按出来。（调试与正式两侧的热键**互不抢占**：跨 dev/prod 边界的抢占会被明确拒绝并给出原因。）

要在真实搜索链路上验证关键字/regex 是不是真能被搜到时，把它打开；调完记得关掉，否则又回到了坑一。

三个细节：

- 调试插件在搜索结果里的**副标题是 `<id> · 调试插件`**（正式插件是 `<id> · 插件`），所以同名的两份是能分辨的——但一眼扫过去仍然容易点错，用完就关。
- 它**始终是 dev 插件**：搜索项内部带 `dev:` 前缀，回车后后端据此路由到**调试窗口**，用的仍然是调试库。不会因为「从主搜索进的」就变成正式插件。
- `runnable = false` 的插件**不会进搜索索引**——点了也打不开的东西出现在搜索里就是欺骗。

## 四、六个 tab 怎么用

选中左侧插件列表里的一个插件后，右侧是六个 tab。

### 4.1 运行（触发模拟器）

列出该插件 `plugin.json` 里的每一个 feature，逐个可以「模拟触发」。你要填三样东西，它们**原样**变成插件页 `onEnter(info)` 收到的 `info`：

| 面板上的字段 | 对应 `info` 字段 | 说明 |
|---|---|---|
| **feature** | `info.code` | 就是 `feature.code`，插件靠它区分是哪个功能被触发 |
| **触发方式** | `info.type` | 关键字 `keyword` / 正则 `regex` / 文本 `text` |
| **模拟 query** | `info.query` | 用户在主搜索框里敲的那串字（换 feature 时会自动带出它的第一个关键字，可改） |

三种触发方式分别怎么模拟：

- **关键字（`keyword`）**：query 填你在 `cmds` 里写的那个关键字（或用户可能敲的近似串）。正式环境里关键字是**模糊匹配**的，所以 `info.query` 未必等于关键字本身，插件不要假设两者相等。
- **正则（`regex`）**：query 填一条**能被你的正则命中**的样本串（比如正则是 `^https?://`，就填 `https://example.com`）。这是最值得模拟的一类——正式环境下你得先把 regex 写对、再在搜索框里造出命中串才能进得去，模拟器让你直接跳到「已命中」的状态去调页面逻辑。
- **文本（`text`）**：query 填任意内容。翻译 / 计算 / 搜索类插件靠它拿用户输入。

选中 feature 后，下面会把**它实际声明了哪些 `cmds`** 摊开给你看（关键字逐个列出，另加 `regex` / `文本` 标签）。一条都没有时会直说「一条都没有 —— 正式环境里它不会被任何输入命中」——这本身就是个很有用的检查。

> ⚠️ **模拟器是「直接指定」，不是「重新判定」。**
> 正式环境里 `info.type` 由后端 `trigger_kind()` 依据 query 与 `cmds` **实际算**出来（regex 命中优先 → 关键字模糊命中 → text 兜底）；模拟器里是**你选什么就传什么**。
> 好处：能直接测到平时难以构造的分支——所以**选了一种该 feature 并没声明的触发方式，模拟器照样让你跑**，只是会明确提示「正式环境里它不会以这种方式被触发」。
> 代价：**模拟器不能替你验证「这个 query 在正式环境里到底会不会命中、会被判成哪一类」**。要验证匹配本身，请开 3.3 的主搜索开关，在真实搜索框里敲。

`runnable = false` 时「运行」按钮是**禁用**的，旁边直接写出禁用原因（把 `error` 级 issue 逐条列出来），不会让你点了没反应；后端也会再拒一次，不存在绕过去打开的路径。

点「运行」之后：

- 插件在标题为 **`<id> - iTools 插件调试`** 的独立窗口里打开——一眼能和正式插件窗区分开，且两者可**同时开着**。
- 窗口默认 **1000 × 700**（比正式插件窗略大），并**按插件分别记住**你调整后的尺寸；这份记忆带 `dev:` 前缀，**不会盖掉同名正式插件的窗口尺寸**。
- 日志里会先落一条 `session.open`，写明本次的 `code` / `kind` / `query`——对着它能确认「模拟器真的按你填的传过去了」。

插件详情头部还有「打开目录」（在资源管理器里定位）——改文件、看构建产物落没落对，比在面板里翻方便。

### 4.2 日志

一条时间线，把 dev 插件页里发生的事按发生顺序摊平。写入方有两个：**插件窗口里的 `bridge.js` 探针**（挂在 `invoke()` 单点上——`window.itools` 的每一个方法最终都经过它，外加 console 与全局异常钩子，批量上报），以及**后端**在探针看不见的地方补记（如会话打开、同步 Mock 的判定结果）。

**能抓到：**

| 类型 | 内容 |
|---|---|
| `api` | 每一次 `window.itools.*` 调用：**API 名**（面板显示的是 `db.set` / `captureRegion` 这种你写的名字，不是 `plugin_db_set` 这种命令名）、入参摘要、返回值摘要、耗时（毫秒，两位小数）、成功/失败。**被后端拒绝（未授权 / 路径越界 / 参数非法）会如实记成失败并带上后端返回的原因**——这正是「点了没反应」最常见的真相 |
| `api`（事件） | **后端推给插件页的事件**（热键触发、设置变更…），方法名形如 `event:hotkey`。有了它，「按了热键没反应」能分清是后端没推来，还是你的回调抛了 |
| `console` | `console.log` / `info` / `debug` / `warn` / `error`。**原始行为完整保留**——DevTools 里照常看得到，探针只是顺手记一份 |
| `error` | 未捕获 JS 异常（带文件行列与 stack）、未处理的 `Promise` 拒绝、**资源加载失败**（`<img>` / `<script>` 404 之类） |

第一条日志固定是 **`probe.ready`**，它把覆盖范围与盲区直接写进时间线里——不用翻文档也能看见。

**摘要与截断规则**（决定你在日志里看到什么形状的东西）：

- 入参/返回值是**结构化摘要**，不是原值：字符串超 200 字符截断、对象最多记 24 个字段、数组最多 20 项、递归最深 3 层（顺带天然规避循环引用），单条总长上限 1200 字符。
- **二进制不记内容**：`ArrayBuffer` / `TypedArray` / `Blob` 只记类型与字节数；`b64` 字段（所有图片/音频入参用的就是这个名字）或超过 4096 字符的字符串一律记成 `«二进制/base64：N 字符 ≈ M 字节，内容未记录»`。一次截图就是几 MB base64，整块塞进日志会直接把内存和 UI 打垮。
- 取值时抛异常的字段（getter / Proxy）记成 `«读取该字段抛异常»`——**绝不让插件的对象把探针带崩**。

**抓不到（这一节请认真读，不要把「日志里没有」当成「没发生」）：**

- **绕过 `window.itools` 门面的直调。** 插件页拿得到 `window.__TAURI_INTERNALS__`，直接 `__TAURI_INTERNALS__.invoke("plugin_db_set", …)` 一样能调通后端（门面从来不是安全边界，后端 capability 白名单才是）。这类调用**一行都不会有**。
  这是**明知并接受**的盲区，不是遗漏：Tauri 2.11 用 `Object.defineProperty(internals, "invoke", { value })` 定义它，描述符默认 `writable:false` / `configurable:false`——严格模式下赋值直接抛 `TypeError`，`defineProperty` 也会失败。硬钩只会把「正在被调试的运行时」本身搞坏。所以探针挂在门面这个唯一出口上，并在 `probe.ready` 里把这件事写明。
- **正式插件窗口（label=`plugin`）的一切。** 探针**只在调试窗口挂载**（靠注入的 `__ITOOLS_DEBUG__` 判定），正式窗口里连一行探针代码都不执行。正式插件页里发生什么，开发者中心看不到，也**不应该**看到。
- **原生侧独立窗口里发生的事**：截图覆盖层、贴图窗口等是另外的 WebviewWindow，不在探针范围内（但插件**发起**它们的那次调用会被记下）。
- **后端内部的执行细节**：你看到的是「这次 invoke 传了什么、拿回什么、花了多久」，不是 Rust 侧的调用栈。
- **页面卸载瞬间没来得及上报的尾部日志。** 探针是**攒批上报**的（攒满 20 条立刻发，否则最多攒 100 毫秒），`pagehide` 与切后台时会尽力冲刷一次，但 IPC 是异步的——**不做「保证送达」的承诺**。
- **上报通道积压时被丢弃的日志。** 队列上限 500 条，超出丢最旧的；但**会如实记一条 `probe.overflow`** 告诉你丢了多少（「那些调用确实发生过，只是没记下来」），不会静静地少几条。
- **探针挂载失败时的一切。** 万一它自己装不上，会用原始 `console.warn` 说明「本次调试不会产生 API / console 日志」，然后当作没有——绝不影响插件本体运行。同理，上报失败也只警告一次，不会重排队死循环。

**取数方式与容量**（决定你什么时候会「少看到几条」）：

- 日志由**后端环形缓冲**（容量 **2000 条**，超出丢最旧的），面板每 **800 毫秒**增量拉取一次（后端有推送时立即拉）。所以它是准实时的，不是硬实时的。面板自己也留最多 **2000** 条（两处刻意取齐，见 `dev/logs.rs` 的 `CAPACITY` 与 `dev-log.ts` 的 `MAX_ROWS`）。
- **管理中心窗口隐藏期间暂停拉取**，恢复后补齐「后端缓冲区里还在的部分」。隐藏太久、期间日志量又大，中间那段就**真的没了**——要盯一段长过程，请让管理中心保持可见。
- `args` / `result` **超过 2000 字符会被后端截断**（一次 `writeFile(base64 图片)` 的入参就可能有几 MB，原样堆进缓冲区会吃光内存、UI 也渲染不动）。面板照原样显示不再加工——看到不完整的 JSON 属正常，不是它坏了。
- `seq` 由**后端统一分配、全局单调递增，清空后也不回退**，所以前端拿上次最大的 `seq` 直接续拉，不会因为清空或乱序上报而漏读/重读。
- 拉取失败时面板**如实显示后端原文并降速重试**，不会把「拉不到」渲染成「没有日志」。
- 可随时清空。

日志**不落盘**——重启 iTools 即清零，别指望它当审计记录或崩溃报告用。

### 4.3 存储（`db` 与 `data` 的区别，最容易搞混的地方）

一个 KV 查看器 / 编辑器。两套 API **分成两张表并排展示、各自标注**——因为把该本地的东西写进了会上云的那套，是这里最常见、也最难自己发现的错误。**这两套不是一回事，也不共享数据**：

| | `db` 视图 | `data` 视图 |
|---|---|---|
| 插件里怎么写 | `itools.db.get/set/remove/keys` | `itools.data.get/set/remove/keys` |
| 后端命令 | `plugin_db_*` | `plugin_data_*` |
| 落到哪张表 | `plugin_kv`（按 `plugin_id` 隔离） | `plugin_data`（按命名空间 `plugin:<id>` 隔离） |
| 会不会上云 | **永远不会**，纯本地 | 正式环境**会**（经 `itools.data.sync()` 或应用的自动同步）；**dev 环境走 Mock，不会** |
| 额外元信息 | 只有 key/value，**不存更新时间** | 带更新时间、脏标记等同步元数据 |
| 该拿它存什么 | 本机配置、缓存、窗口状态这类**换台机器就该重来**的东西 | 用户内容这类**换台机器该跟过去**的东西 |

一句话选型：**默认用 `db`；只有你确实希望这份数据跟着用户的云账号走，才用 `data`。**

面板上能做的事，全部作用于**调试库**：

- **查看**：列出该插件的所有键，显示值（JSON 文本）与字节数（后端真实统计，不是估算）。更新时间只有底层真的记了才显示——**没有记录时显示 `—`，不会编造一个时间**（`db` 那套 KV 本来就不存时间戳）；
- **改 / 删 / 新增**：值按 **JSON 文本**填。桥接层的 `itools.db.set(k, v)` 做的就是 `JSON.stringify`，所以插件写进去的一定是 JSON——写一个字符串要填 `"abc"`（带引号），不是 `abc`。
  编辑框会**实时校验并提示**是否合法 JSON；**不合法也允许你保存**（有时你就是要造一条脏数据测插件的容错），只是会明确告诉你「插件读取时可能解析失败」。这是「如实告知 + 不越权阻拦」，不是校验没做。
- **清空**：清掉该插件在调试库里的**全部**数据（`db` 与 `data` 两边一起清）。**两步确认**：第一次点变成「确认清空？（db + data）」，3 秒内再点才真清。
- **导出 / 导入**：导出弹出一个只读文本框给你复制（后端导出的原始 JSON），导入是把这段 JSON 粘回去。用来做「造一份初始数据 → 反复回到同一起点重跑」的固定装置，比每次手敲快得多。**没有文件选择器**，走剪贴板。

> 存储 tab 只看得见、也只改得动**调试库**。想看正式库里的插件数据请去「数据用量」页；开发者中心**没有**读写正式库的入口，这是故意的。

### 4.4 权限

列出该插件 `plugin.json` 里 `permissions` 声明的每一项，逐项开关。

**只影响调试环境。** 这里的授权写进独立的 dev 授权表，与「插件管理」页里正式插件的授权表是两份数据；在这里授权 `network`，不会让同名的正式插件获得 `network`，反之亦然。

它解决的是一个具体的开发问题：**验证「用户没授权时，我的插件降级得体不体面」**。授权是一个开关的事，你可以来回切，反复走 `catch` 分支，确认未授权时给的是可读提示而不是白屏。

> ⚠️ **授权判定是双条件，面板上开了未必就通。**
> 后端判定是「用户授权过」**且**「插件**当前**的 `plugin.json` 仍声明了该 permission」，缺一不可（防的是同名覆盖安装继承旧授权）。所以：`plugin.json` 里没写 `"permissions": ["network"]` 的插件，即便你在面板上把开关打开，`itools.fetch` 照样被拒。
> 这不是 bug，正式环境行为一致。遇到这种情况先去清单校验里看有没有相应的提示——你多半是漏声明了。

### 4.5 同步 Mock

`itools.data.sync()` 在 dev 环境下**不连任何服务端**，返回由本 tab 配置的结果。

> Mock 配置是**全局的、不区分插件**——它挂在开发者中心的整体配置上，改了对所有 dev 插件同时生效。同时调两个插件时留意这一点。

可配四种模式：

| 面板上的选项 | `mode` | 返回 | 用来测什么 |
|---|---|---|---|
| 同步成功 | `success` | `synced: true` + 你设定的「伪造条数」`pushed` / `pulled`（**只在这个模式下有意义**，是你填的假值，不反映调试库里真实有多少条） | 正常路径：同步成功后 UI 怎么反馈、条数怎么展示 |
| 未登录 | `notLoggedIn` | `synced: false`，对应正式环境的 `reason: "not_logged_in"` | 用户没登录云账号时的降级——**这是最常见的真实情况**，一定要测 |
| 离线 | `offline` | `synced: false`，对应正式环境的 `reason: "offline"` | 断网 / 服务端不可达 |
| 同步失败 | `fail` | `synced: false`，`reason` 用你自己填的那段文本 | 造任意 reason，比如 `cloud_not_configured` / `session_expired` / `partial`，把你的错误分支走全 |

外加一个 **人为延迟（毫秒）**：拉长同步耗时，用来验证「同步中」的 loading 态、按钮防重复点击、以及超时文案——真实网络里这些分支很难稳定复现，Mock 里填个 3000 就行。**上限 10000 毫秒**（真实同步的 HTTP 超时是 30 秒，但调试里没必要卡这么久）；伪造条数上限 100000。

> 超出上限的值会被**夹紧**，而 `dev_get_mock` 返回的是**夹紧后的真实值**——不会出现「你设了 60 秒、界面显示 60 秒、实际只等 10 秒」这种假控件。

Mock 返回的**就是真实的 `SyncResult` 结构体**（同一个类型，不是另造一个），形状为 `{ synced, reason?, pushed, pulled, message? }`。真实环境里 `reason` 的取值域是 `cloud_not_configured` / `not_logged_in` / `offline` / `session_expired` / `error`（全量同步全失败时还有 `partial`）。**插件不要 `if (reason === "offline")` 硬编码穷举后把英文原文甩给用户**——请把 `message` 展示给用户，`reason` 只用于你自己的分支逻辑。

> ✅ **`itools.account.state()` 会跟着 Mock 走**：模式不是「未登录」就报已登录。否则你把 Mock 设成「同步成功」、插件却因为本机真实账号没登录而根本不进同步分支，模拟器就白做了。调试会话全程不读真实登录态、不联网。

### 4.6 发布（提交审核）

调好了就在这里提交上架。这个 tab 是**唯一**会联网、也是唯一会把你的代码发出去的地方。

#### 提交审核会发生什么

```
点「提交审核」
  → 客户端把这个调试目录打成 zip（跳过 .git / node_modules / 点开头的文件）
  → 上传到你在「设置 → 网络」配的那台服务器（需要先登录云账号）
  → 服务端机械校验：格式、清单、不含可执行文件、路径安全、版本号必须高于线上
  → 通过后交给大模型通读代码：有无恶意行为、申请的权限是否名副其实、描述是否相符
  → 通过即自动发布到插件市场，用户可以直接安装
```

上传接口**立即返回**（审核要几十秒到几分钟），提审单先是「审核中」，出结果后状态才变。点「刷新状态」查看进展。

> ⚠️ **提审需要先登录云账号。** 插件的归属与审核结果都挂在账号上，而且**同名插件只有首次上线它的那个账号才能更新**——别人拿同一个 `name` 提交会被服务端直接拒（403）。这不是洁癖：客户端是按插件名归属用户授权与数据的，让别人顶包等于把受害插件的用户授权直接送出去。

#### 五种状态，含义各不相同

面板上的大徽标就是当前状态。**线上状态优先展示**（它是用户真正看得到的事实），其次才是最近一次提审的进展：

| 徽标 | 含义 |
|---|---|
| **未提审** | 从没提交过，也不在市场里 |
| **审核中** | 服务端正在读你的代码。面板会告诉你在审的是哪个版本、什么时候提交的 |
| **已上线 vX.Y.Z** | 审核通过，市场里当前提供的就是这个版本 |
| **已驳回** | 没通过，`message` 是服务端给的原因原文（面板原样展示，不改写） |
| **待人工处理** | ⚠️ **审核没能完成**——不是通过，插件**没有**上线 |
| **已下架** | 上过线但被维护者下架了，面板会显示下架原因 |

> 🚨 **「待人工处理」绝不等于「通过」。** 服务端在这四种情况下会落这个状态：审核模型没接入（服务端没配 key）、模型调用失败、模型返回的裁决解析不了、服务重启把审核打断了。这四种都是「这次没审成」，插件不会上线，需要维护者人工处理。面板用告警色显示它，就是为了不让它被读成绿色的「过了」。

#### 提交前自检

面板会先跑一遍本地自检，列出两类：

- **阻断**：服务端**一定**会拒的（缺 `index.html`、`name` 不合法、版本号不高于线上、清单有 `error` 级问题）。有阻断项时「提交审核」按钮**禁用并写明原因**。
- **提醒**：不阻断提交，但值得先看一眼（第五节那些 `warn`）。

> ⚠️ **自检通过不代表会过审。** 自检只做本地能判定的机械检查；代码有没有问题是服务端的大模型说了算，本地看不出结论。别把绿色的「没有发现问题」读成「稳过」。

按钮在这几种情况下是禁用的，旁边直接写原因，不做「看着能点、点了没反应」的控件：

- 插件当前跑不起来（`runnable = false`）；
- 自检有阻断项；
- 没登录云账号 / 服务器地址读不到；
- 上一版还在审核中（出结果才能提交下一版）；
- 版本号不高于已上线的版本。

#### 提审记录

下面列出这个插件的历次提交（新→旧），每条可以展开看**模型裁决原文**：

- **逐条问题**：等级（阻断 / 严重 / 次要 / 提示）、出问题的文件、描述、以及模型引用的代码片段；
- **权限声明核对**：每个 `permissions` 是「已声明且确实用到」「已声明但代码里没用到」还是「代码里用到了但没声明」。

这一段是原样展示模型说了什么，不做美化、不吞细节——被驳回时你需要看到的是真实依据，而不是一句「未通过」。

#### 版本号

**改了代码就升 `plugin.json` 的 `version`。** 服务端要求新版本号严格高于线上版本，否则直接拒（客户端的更新检查也只比这一个值）。预发布后缀（`-beta` / `-rc`）不被识别，别用，理由见 [`插件分发规范.md`](插件分发规范.md) 第五节。

## 五、清单校验：`issues` 到底能定位到多细

每个 dev 插件卡片上都挂着一组 `issues`，两个级别：

两个级别，含义是**硬绑定**的：

- **`error` ⟺ `runnable = false`**（`runnable` 就是「一条 error 都没有」）。「运行」按钮被**禁用**，旁边直接列出禁用原因，不会让你点了没反应；这类插件也不会进主搜索。
- **`warn`**：能跑，但**发布前必须清**——`warn` 里有好几条在正式环境是「直接拒绝加载」。

**能判成 `error` 的只有三种**（都是「连跑都跑不了」的）：

| `field` | 什么情况 |
|---|---|
| `index.html` | 缺少 `index.html`——**唯一一条与清单无关的致命问题** |
| `plugin.json` | 读不出来 / 不是合法 JSON（会提醒你「JSON 不支持注释与尾逗号」）/ 结构不符合规范 |
| `id` | 目录名与另一个调试插件冲突，本条不会被加载（先扫到的那个胜出） |

**其余的清单字段问题一律是 `warn`** ——这正是「调试环境放宽」的落点（见 5.1）：清单写得再糙也让你先跑起来看效果，同时把后果写在脸上。

`field` 精确到**字段路径 + 数组下标**，直接对着 `plugin.json` 找就行：

```
name                    → name 为空 / 与目录名不一致
description             → description 为空（搜索结果里没有说明文字）
icon                    → 图标不可用（缺失 / 扩展名不在白名单 / 超大小上限）→ 回落兜底字形
permissions[2]          → 第 3 条声明的是个**不存在的能力名**
features                → features 为空
features[1].code        → 第 2 个 feature 的 code 为空或重复
features[1].cmds[2]     → 第 2 个 feature 的第 3 条触发规则有问题
features[1].cmds        → 这个 feature 一条可用触发方式都没有
index.html / plugin.json / id  → 不是清单字段，是文件或 id 层面的问题
```

`cmds` 那一级能查出来的具体毛病：**空关键字**、**`{"type":"regex"}` 缺 `match`**、**正则编译不过**（附正则错误原文）、**用了不参与匹配的触发类型**（会告诉你当前只支持裸字符串关键字、`{"type":"regex"}`、`{"type":"text"}`）。

`permissions` 会按已知能力清单核对，可用的只有 **`runCommand` / `network` / `screen-capture` / `audio-capture` / `hotkey`** 这 5 个；写成别的（拼错、臆造）会被点名——正式环境里这种声明是**静默失效**的，很难自己发现。

> `message` 是**后端原文**（大多带上「正式环境会怎样」的后果提示），面板不改写、不吞掉。看不懂的时候以 message 为准，别只看 field。

### 5.1 ⚠️ 开发环境比正式环境**放宽**了哪些校验

**这一节是全文最重要的一节。**「在开发者中心里能跑」**不等于**「放进 `plugins/` 就能用」——因为开发环境刻意放宽了一部分校验，把「直接跳过不加载」降级成了「加载并告警」。

放宽的理由很实际：正式环境的 `scan_plugins` 遇到不合格的插件是**静默跳过**（只往 `itools.log` 写一行）。对开发者来说，这表现为「我明明把插件放进去了，它凭空消失了」，而且没有任何界面提示，排查成本极高。开发环境把这些情况**全部加载出来 + 把原因摆在脸上**。

| 校验项 | 正式环境（`plugins/`） | 开发者中心 |
|---|---|---|
| **`plugin.json` 的 `name` ≠ 目录名** | **直接跳过，插件不加载**（`scan_plugins` 显式校验，表现为「插件凭空消失」） | **照样按目录名加载**，只报一条 **`warn`** |
| **`name` 为空** | 拒绝加载 | 照样加载，`warn` |
| **`features` 为空** | 拒绝加载 | 照样加载（搜不到也进不去），`warn` |
| **`feature.code` 为空 / 重复** | 拒绝加载 | 照样加载，`warn` 并标出 `features[i].code` |
| 缺 `index.html` | 加载失败，跳过 | 加载出来，**`error`**，`runnable = false` |
| `plugin.json` 语法 / 结构错误 | 加载失败，跳过 | 仍列在目录下，**`error`** 并附解析器原文 |
| feature 无任何**有效**触发方式（如只写了 `{"type":"keyword"}` 对象形态、或只有 `files`/`img`） | 该 feature 被静默丢弃、搜不到（仅日志一行） | `warn` 指到 `features[i].cmds`，并提示「仍可用触发模拟器手动进入」 |
| 无效 regex / regex 缺 `match` | 该条规则被静默丢弃（仅日志一行） | `warn` 指到 `features[i].cmds[j]`，附正则编译错误 |
| `permissions` 里写了不存在的能力名 | **静默失效**，无任何提示 | `warn` 指到 `permissions[i]`，并列出可用的 5 个 |
| `icon` 不可用（缺失 / 扩展名非白名单 / 超上限 / 指向目录外） | 不显示图标，日志一行 | 不显示图标（回落兜底字形），`warn` |
| `description` 为空 | 无提示 | `warn`（搜索结果里没有说明文字） |

看出规律了：**正式环境「拒绝加载」的那四条（`name` 不符 / `name` 空 / `features` 空 / `code` 空或重复），在开发者中心统统只是 `warn`。** 它们不影响 `runnable`，插件照跑不误——但**放进 `plugins/` 就是「插件不存在」**。

**所以：发布前请把 `issues` 清到零——`warn` 尤其要清。** 最典型的翻车是 `name` ≠ 目录名：在开发者中心里它只是一条黄色告警，在正式环境里是插件直接消失、且**没有任何界面提示**。

## 六、从调试到发布

调试通过之后，走这条路：

1. **把 `issues` 清空**（含 `warn`）。重点核对第五节表格里那几条「开发放宽、正式严格」的。
2. **目录名与 `plugin.json` 的 `name` 对齐**，两者必须逐字符相等（小写字母数字连字符）。这一步单独列出来，因为它是最常见的失败原因。
3. **确认存储选型对**：本机状态用 `itools.db.*`，需要跟着云账号走的用户内容才用 `itools.data.*`。调试期存储 tab 里那些测试键值**不会**跟着插件走——它们只在调试库里，正式环境是一个干净的空库。
4. **确认权限声明齐**：调试时在权限 tab 打开过的每一项，都必须写进 `plugin.json` 的 `permissions`，否则正式环境用户就算授权也用不了（双条件判定，见 4.4）。
5. **确认同步分支不是只在 Mock 下正确**：Mock 覆盖了 reason 分支，但**没覆盖真实网络**。涉及 `data.sync()` 的插件，发布前请在真实账号下至少跑通一次「已登录 → 同步成功」与「未登录 → 降级提示」。
6. **落地**，三选一：
   - **上架插件市场（推荐）**：在「发布」tab 点「提交审核」，服务端审完自动上线，用户在「插件市场」页一键安装。见 4.6。
   - 自用：把目录拷进 `plugins/`（或用环境变量 `ITOOLS_PLUGINS_DIR` 指定的根），托盘 →「重新加载插件」即可；
   - 自行分发：推到 Git 仓库，用户粘一行 URL 直装（不经市场、不经审核）。URL 语法、仓库布局、安全限制见 **[`插件分发规范.md`](插件分发规范.md)**。

**无论走哪条路，改了代码都要升 `plugin.json` 的 `version`**——更新检查只比这个值，市场提审还会硬性要求新版本高于线上版本。

> 开发者中心**不会帮你推仓库、也不会把 dev 插件拷进 `plugins/`**。它做的是「打包 + 上传 + 查状态」这一条链路；本地转正仍是手动的两步（改对目录名 + 拷过去），避免把半成品误落到正式插件根。

## 七、已知限制与盲区（诚实清单）

标 ❌ 的是完全没有；标 ⚠️ 的是**行为与直觉不符 / 只有受限形态**，同样不能当成完整能力去依赖：

- ⚠️ **探针只覆盖 `window.itools` 门面，且这是设计上无法消除的盲区。** 插件页可以直接用 `window.__TAURI_INTERNALS__.invoke(...)` 绕过门面调后端，这类调用**日志里一行都没有**。之所以不去硬钩 `__TAURI_INTERNALS__.invoke`：Tauri 把它定义成不可写不可配置，钩它只会把正在被调试的运行时搞坏（详见 4.2）。门面本来就不是安全边界（后端 capability 白名单才是），探针挂在门面上是「可观测性」而非「拦截」。**日志的完整性以「插件老实用 `itools.*`」为前提。**
- ⚠️ **`bridge.js` 探针没有自动化测试覆盖。** 它是注入插件页的 JS，跑在真实 WebView 里，本项目的 `cargo test` / `tsc` 都测不到它。探针的正确性**只能靠真机验证**——如果你发现某类调用该记的没记，那很可能是真的漏了，请反馈。
- ⚠️ **日志的送达是「尽力而为」，不是保证。** 攒批上报 + 页面卸载时尽力冲刷；队列积压超 500 条会丢最旧的（但会记一条 `probe.overflow` 告诉你丢了多少）；探针自身挂载失败或上报失败时只警告一次，之后当作没有。**「日志里没有」不等于「没发生」**——这句话在面板和 `probe.ready` 里都写着，请当真。
- ⚠️ **入参 / 返回值是摘要，不是原值。** 二进制与 base64 只记类型和体量、不记内容（截图/录音动辄几 MB，记下来会把内存和 UI 打垮）；深层结构会被折叠。需要看真实内容请自己 `console.log` 关键片段。
- ⚠️ **插件设置在调试环境里只有默认值。** 开发者中心**没有设置 tab**，`itools.settings.get/all()` 在调试会话里只返回调试插件目录 `settings.json` 的 **schema 默认值**，读不到（也不该读到）正式插件那份用户配置。要测「用户改过设置」的分支，只能临时改 `settings.json` 里的 `default`。这是本轮的已知缺口。
- ⚠️ **Mock 只接管 `itools.data.sync()` 与 `itools.account.state()`。** 应用层的**自动后台同步**不会因为 Mock 改变行为——它走的是正式库，本来就跟 dev 无关。
- ⚠️ **日志不落盘、会滚动淘汰、会漏。** 后端环形缓冲 2000 条、面板也 2000 条，超出丢最旧的；重启即清零；插件窗口被强杀时最后一批未上报的会丢；**管理中心窗口隐藏期间暂停拉取**，隐藏太久那段就补不回来了。不要拿它当审计或崩溃报告用。
- ⚠️ **长参数/长返回值超过 2000 字符会被后端截断。** 面板照原样显示不再加工，所以你可能看到不完整的 JSON。要看完整内容请自己在插件里 `console.log` 出关键片段（console 输出同样受这条截断限制，但你可以只打你要的那部分）。
- ⚠️ **调试环境不隔离「真实副作用」。** 除 3.1 列出的那几类外的能力（剪贴板、截图、贴图、OCR、通知、热键、录音、录屏、`runCommand`、`itools.fetch`）**全部走正式实现**：dev 插件写剪贴板是真的写，起进程是真的起，联网是真的联。这是刻意取舍（见 3.1），但请知情。
- ⚠️ **触发模拟器不验证匹配本身。** `info.type` 是你选的，不是算出来的；模拟器进得去，不代表正式环境下用户敲那串字真能搜到你的插件。要验证匹配请开主搜索开关走真实链路（见 4.1、3.3）。
- ❌ **没有断点 / DOM 检查器 / 网络面板。** 开发者中心不是 DevTools 替代品，它给的是**调用日志与数据视图**。需要断点调试页面 JS 时，请在 `tauri dev` 下用 WebView2 的开发者工具（`console.*` 的原始输出完整保留，DevTools 里照常看得到）。
- ❌ **不支持热重载（改文件自动重扫）。** 改了插件文件需要手动点「重新扫描」；改了 `index.html` / JS 后重新点「运行」即生效（协议响应沿用 `Cache-Control: no-store`，不会被 WebView 缓存卡住旧版本）。
- ⚠️ **插件在运行时分辨不出自己在调试环境里。** `itools.platform.isDev` 表示的是「iTools 本身是不是 debug 构建」，**不是**「我在不在调试环境」；门面没有暴露判断调试环境的开关。所以不要写「调试环境走 A 分支、正式环境走 B 分支」的代码——也不该这么写，两边行为一致才是这套环境的意义。
- ⚠️ **「发布」tab 只做打包上传与状态查询，不做本地转正。** 它不会把 dev 插件拷进 `plugins/`、不会帮你推 Git 仓库。见 4.6 与第六节。
- ⚠️ **提审用的是「当前磁盘上的目录内容」，不是你上次点『运行』时的那份。** 打包发生在点击的那一刻，改了文件不用重新扫描就会被带上去——反过来说，改了一半没保存也会被一起传上去。
- ⚠️ **打包会跳过 `.` 开头的文件/目录与 `node_modules` / `.git` / `.vscode` / `.idea` / `__pycache__`。** 如果你的插件**真的**依赖一个点开头的文件（如 `.htaccess` 之类），它不会进包，装到用户那儿就没有——这是刻意的取舍（不这么跳，`.env` 这类东西会被顺手传上去）。
- ⚠️ **自检不预测审核结果。** 它只拦「服务端一定会拒」的机械项；代码审核由服务端的大模型做，本地看不出结论。
- ⚠️ **审核状态全部来自服务端，查不到就显示查不到。** 未登录、服务器不可达、索引拉不到时，面板显示的是**真实错误原因**，不会拿本地信息拼一个看起来合理的状态。
- ❌ **dev 插件不参与更新检查。** 它们没有安装来源记录（`.installed.json` 只管正式插件根），「检查更新」与开发者中心无关。
- ⚠️ **调试数据不迁移。** 调试库里的数据不会、也不应该被带进正式环境。需要预置初始数据请用存储 tab 的导出/导入，或者让插件自己在首次运行时初始化。
