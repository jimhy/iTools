## 一、背景与目标

### 1.1 问题

第三方作者反馈：除了纯计算类工具（翻译、编解码、格式化），大部分想做的东西做不了。典型受阻场景：

| 想做的工具 | 卡在哪 |
|---|---|
| 翻译 | ✅ 可做 |
| 磁盘清理 | 文件读写只能在插件沙盒目录，碰不到 `C:\Windows\Temp`、回收站、浏览器缓存 |
| APK 安装 | `runCommand` 拿不到 `adb` 的输出、退出码；网页拖入的文件拿不到真实路径 |
| 文件传输 | 需要起 HTTP 服务让手机连进来，插件只能当客户端 |
| 视频工具 | ffmpeg 几十 MB、模型几百 MB 进不了插件包；调起长任务也拿不到进度和结果 |

### 1.2 目标

让第三方作者能用 iTools 开发**真正的软件**并分享，而不只是小面板。同时不牺牲 iTools 相对同类产品的安全优势。

### 1.3 衡量标准

- 上面 5 个场景中，除「视频工具」需要 runtime 托管外，其余应在第一、二波内全部可做。
- 新增能力不得让「用户对插件行为失去可见性和控制权」。

## 二、架构路线：能力白名单 + 原生扩展逃生舱

### 2.1 两条路线的对比

**uTools 的路线：preload 全开放 + 明文审核**

`preload.js` 是跑在渲染进程前的 CommonJS 脚本，直接拿到 Node.js 16 全套能力（`fs`、`child_process`、`http`、任意 npm 包、Electron renderer API），挂到 `window` 上供页面调用。

安全依靠三条：

1. preload 及其依赖的源码**必须明文可读**，禁止压缩、混淆
2. 提审时人工 + 机器审核
3. 用户安装即信任

**iTools 现有路线：纯前端沙盒 + 能力白名单**

插件是受限自定义协议页（严格 CSP，不能引外部资源、默认不能联网），所有系统能力经 `window.itools.*` 调用，后端 Rust 逐项做权限门禁，权限按插件、按能力独立开关。

### 2.2 为什么不照抄 preload

**工程上不成立**：Tauri 架构里没有 Node.js。要做 preload 等于内嵌一个 Node/Deno 运行时，体积与内存优势当场归零 —— 而那正是 iTools 相对 Electron 系产品的核心卖点。

**安全模型上是降级**：preload 是 all-or-nothing。给了就是全给，且**装完无法按能力撤销**。iTools 现有的细粒度权限（`screen-capture` / `audio-capture` / `runCommand` / `network` 各自独立开关、随时可关）是更强的模型，不应放弃。

### 2.3 但白名单有一个真实代价

**开发者必须等平台开 API**。作者想做的每件事都要排队等宿主实现 —— 这是生态速度的根本瓶颈，也正是本文档的由来。

### 2.4 结论：主路线 + 逃生舱

| | 覆盖面 | 机制 |
|---|---|---|
| **主路线** | 目标 90%+ 插件 | 细粒度能力 API，安全、可审计、可单项撤销 |
| **逃生舱（L3 原生扩展）** | 少数确有需要的插件 | 通用 fs / exec / net 面，代价是强审核 + 明示 + 常驻标识 + 市场单独分区 |

与 uTools 的关键差别：**逃生舱是例外通道，不是默认路径**；用户在安装时就被明确告知该插件拥有的能力范围。

### 2.5 关于「明文审核是否足够」的判断（重要）

内部曾有分歧，此处记录结论与理由，供后续决策参考。

**明文审核确实有效**，这一点没有争议：uTools 以此模型运行多年、生态活跃、未出现大规模安全事故。明文源码 + 人工审核对绝大多数恶意行为是有效防线。

**但审核在原理上覆盖不到三块**：

1. **审核的是提审那一刻的代码，不是运行时执行的代码。**
   preload 有 `require()`、有网络，因此可以写出提审时完全无害的代码：

   ```js
   const code = await fetch(cfg.updateUrl).then(r => r.text())
   new Function(code)(api)   // 上架后远端换成任意内容
   ```

   这不是审核不严，是审核看不见。npm（event-stream）、VSCode 插件、Chrome 扩展都是明文源码 + 人工审核的生态，都发生过此类事件。

2. **明文能判「代码做了什么」，判不了「这么做正不正当」。**
   一个磁盘清理插件遍历全盘、读文件、上报统计 —— 每一行都合理，组合起来是数据外泄。正当的文件同步插件与窃密插件，代码结构可以一致，差别只在服务端。审核者面对的是判断题，错误率不随代码明文而下降。此外允许打包 npm 源码时，实际无法逐行审几万行第三方代码。

3. **审核是概率防线，权限是损害半径。** 两者不互相替代：
   - 用户发现某插件在开摄像头 → 关掉那一项，其他功能照用
   - 平台发现某能力被批量滥用 → 全局降级该能力，不必下架几十个插件
   - all-or-nothing 下唯一手段是下架 + 卸载，已发生和正在发生的损害都收不回来

**因此本路线采纳的判定是**：明文审核作为逃生舱的**主防线**成立，但必须补上一条把审核前提锁死的硬约束 —— 见 5.2「禁止运行时动态代码加载」。补上之后逃生舱可以放心做，故其优先级从第四波提前到**第二波**。

### 3.4 分发约束（`插件分发规范.md`，设计新能力时须遵守）

- 归档 zip ≤ 32 MB，解压总量 ≤ 32 MB，单文件 ≤ 16 MB，条目数 ≤ 4000
- **禁止携带 23 类可执行 / 脚本 / 快捷方式扩展名**，命中整包拒绝
- 安装后**所有权限一律默认未授权**

因此：任何需要二进制的能力（ffmpeg / adb）**只能走宿主托管的 runtime 机制**，不能让插件自带 —— 这条约束不放宽。

## 四、能力域清单

风险级说明：**L0** 无需授权 · **L1** 装后开关即可 · **L2** 用时授权 + 运行时指示 · **L3** 强审 + 每会话确认 + 审计日志。
波次见第七章。

### 域 1 · 文件与路径 ★当前最大短板

主路线是**用户选择即授权**（参照浏览器 File System Access 模型），而不是开放任意路径。

| 能力 | API 草案 | 权限 | 底座 / 成本 | 风险 | 波次 |
|---|---|---|---|---|---|
| 用户选目录/文件 → 持久句柄 | `itools.pickDir(opts): Promise<Scope>`<br>`itools.pickFile(opts): Promise<Scope>`<br>scope 内自由读写，可持久保存复用 | `fs-user-scope` | `rfd` 已有，低 | L2 | 一 |
| 命名路径白名单 | `itools.paths.resolve(name)`<br>name ∈ temp / downloads / desktop / documents / appData / recycleBin / browserCache | `fs-named-path`（读写分开） | 新增，低 | L2/L3 | 一 |
| 送回收站 | `itools.trash(paths: string[]): Promise<void>` | `fs-trash` | Win32 `SHFileOperation`，低 | L2 | 一 |
| 真删（危险） | 不开放给插件。由宿主弹确认框列出条数与体积后执行 | — | — | — | 一 |

### 域 11 · 远程控制 —— 不做成通用 API

海风哥点名的能力，单独设计。它拆开看是几块已有 / 规划能力的组合：屏幕捕获（已有）+ 编码推流（缺）+ 输入注入（规划）+ 网络信令（缺）。

**不把这四样作为自由组合的 API 开给任意插件**。原因很直白：这四样凑齐就是一个完整的远控木马，任何通过审核的插件都能悄悄组装出来。

**正解是做成宿主级受控原语**：

- 连接、配对码、鉴权、端到端加密、中继，**全部由宿主实现**，插件碰不到
- 会话期间强制显示悬浮条：「XX 正在远程控制本机」+ 一键切断，**不可被插件隐藏**
- 插件只拿到会话生命周期事件和 UI 定制权，拿不到原始输入注入通道
- 审核规则：当同一插件同时申请 `input-inject` + `screen-capture` + `network` 时，自动升级为人工强审

这样远程控制作为 iTools 的**招牌功能**存在，插件可围绕它做增强（设备管理、多端剪贴板、文件互传），但没人能拿它当武器。

|---|---|---|---|
| 发起 / 接受远程会话 | `itools.remote.host()` → 配对码；`itools.remote.connect(code)` | `remote-session` | 四 |
| 会话事件与 UI 定制 | `itools.remote.onSession(cb)` | `remote-session` | 四 |

## 五、L3 原生扩展（逃生舱）设计

### 5.1 定位

白名单能力覆盖不到的少数场景的出口。**是例外通道，不是默认路径**。

获得逃生舱资格的插件，可使用一套通用的原生接口面（完整 `fs`、`exec`、`net`），能力接近 uTools 的 preload。

### 5.2 准入硬约束（核心）

明文审核要成为有效防线，前提是「**审核过的代码 = 实际运行的代码**」。这个等式必须用工程手段锁死，否则审核在原理上就被架空（理由见 2.5）。

**因此逃生舱插件必须同时满足：**

1. **源码明文** —— 禁止压缩、混淆；第三方依赖同样须为明文源码
2. **禁止运行时动态代码加载**（最关键的一条）
   - 静态检查禁用 `eval`、`new Function`、动态 `import()`
   - 禁止 `require` 包外路径
   - 运行时由宿主拦截远程代码执行
   - **依赖必须随包提交，不许运行时下载**
3. **人工强审** —— 不走纯模型审核
3. **安装时明示** —— 红色警告页，逐条列出该插件可做什么（「可访问你的全部文件」「可执行任意程序」「可联网」）
4. **运行时常驻标识** —— 状态栏显示该插件正在使用原生扩展，可一键停用
5. **市场单独分区** —— 与普通插件区分展示，用户可在设置中「禁止安装原生扩展插件」
7. **审计日志** —— 原生接口调用记录可查

### 5.3 与 uTools preload 的差别

| | uTools preload | iTools 逃生舱 |
|---|---|---|
| 是否默认路径 | 是，任何插件都能用 | 否，需申请与强审 |
| 运行时动态加载代码 | 允许（文档明示可下载外部源码） | **禁止**，静态检查 + 运行时拦截 |
| 装后能否按能力撤销 | 不能 | 可停用原生扩展，其余功能不受影响 |
| 用户是否明确知情 | 一般提示 | 安装红色警告页 + 运行时常驻标识 |
| 市场展示 | 混排 | 单独分区，可全局禁止安装 |

### 5.4 尚待确定

- 原生接口的具体形态：是内嵌轻量 JS 运行时，还是把 Rust 侧的通用 `fs` / `exec` / `net` 用一组 API 暴露给插件页（后者与现有架构一致，倾向此方案）
- 静态检查的实现位置：提审服务端 + 客户端安装时双重检查
- 已上架逃生舱插件的复审周期

## 六、权限治理体系

能力大幅扩张后，治理层必须同步升级，否则开得越多风险越集中。

### 6.1 分级

| 级别 | 典型能力 | 审核 | 授权方式 |
|---|---|---|---|
| **L0** | 纯前端、图像处理、压缩、系统只读信息、DIP 转换、子输入框 | 自动 | 无需授权 |
| **L1** | `network`、剪贴板读写、通知、SQLite、动态指令 | 快审 | 装后开关 |
| **L2** | 屏幕 / 音频 / 摄像头捕获、用户选择的文件 scope、命名路径读、`serve`、窗口管理、上下文感知、后台常驻 | 模型 + 人工双审 | **用时授权 + 运行时指示** |
| **L3** | `exec`、runtime、输入注入、进程结束、命名路径写、裸 socket、系统管理、原生扩展 | 强人工审 | **每会话确认 + 审计日志** |

### 6.2 四条硬约束

1. **插件间数据隔离** —— 一个插件只能读写自己的数据，公共数据须由拥有者显式公开且只读。**这是红线，详见 6.5。**
2. **运行时指示器** —— 摄像头 / 麦克风 / 屏幕 / 远控 / 原生扩展使用中，必须有不可隐藏的可视指示 + 一键掐断（参照 macOS 绿灯）。**这是隐私底线，不接受「先上线后补」。**
3. **审计日志** —— 哪个插件、何时、用了什么高危能力，用户可查、可导出。
4. **契约标记** —— 项目已有 `contract-snapshot.json` / `contract.rs` 契约快照机制。新能力上线时标注 `stable` / `experimental`，避免能力爆炸后 API 失控。

### 6.3 组合风险规则

单项能力无害、组合起来危险的情况要专门识别：

| 组合 | 含义 | 处理 |
|---|---|---|
| `input-inject` + `screen-capture` + `network` | 等价于远控木马 | 自动升级人工强审 |
| `fs-user-scope` + `network` | 数据外泄能力 | 审核重点关注上传目标 |
| `clipboard-watch` + `network` | 剪贴板窃取（含密码、验证码） | 审核重点关注 |
| `background` + 任意 L3 | 无 UI 的高危常驻 | 强审 + 常驻标识 |

### 6.4 权限声明与文案

`plugin.json` 的 `permissions` 数组扩展为当前全部能力标识。管理中心需为每个标识提供**面向用户的中文说明**（现有 `src/admin/market.ts` 已有 `"screen-capture": "屏幕捕获"` 这类映射，按此扩充），并说明**不授权时插件会怎样降级** —— 分发规范第 7 条已要求插件在未授权时优雅降级，不得白屏或静默失败。

### 6.5 插件间数据隔离（红线）

**原则：一个插件只能读写自己的数据。除非是明确公开的公共数据，否则读不到任何其它插件的数据。**

这条是硬约束，不是「尽量」。能力开放过程中每加一项 API，都要回答「它会不会成为跨插件读数据的新通道」。

#### 6.5.1 现状：哪些已经隔离好了

以下机制经核实**真实有效**，隔离由后端判定、前端无法伪造：

| 面 | 机制 | 位置 |
|---|---|---|
| 调用者身份 | `caller_session()` 按 **webview label** 反查会话，插件页无法自称是别人 | `plugin/commands.rs:980` |
| `db` / `data` KV | `pkv_get(&session.id, &key)`，按插件 id 分区 | `plugin/commands.rs:775` 起 |
| 沙盒文件 | 正式会话锁在 `plugin-data/<id>/files`，调试会话锁在 `dev/plugin-data/<id>/files`；`sandbox_relative()` 禁绝对路径、盘符、`..` | `plugin/commands.rs:505`、`:995` |
| `settings` | 按插件读取自己的 schema 与值 | — |
| 高危授权 | 按**调用窗口当前的插件会话**判定，插件 A 把插件 B 的页面 iframe 进来也按顶层插件的授权算，杜绝借道 | `plugin/commands.rs` `plugin_fetch` 注释 |
| 录音 / 录屏归属 | 用「插件 id + dev 标志」的完整会话身份校验，别的插件不能停掉、也不能取走本插件的录音 / 录屏产物 | `plugin/audio.rs`、`record.rs` |

#### 6.5.2 现存缺口：浏览器级存储（需修复）

**问题**：插件页 URL 是 `itplugin://localhost/<plugin_id>/<path>`（Windows 上表现为 `http://itplugin.localhost/...`）。
**`plugin_id` 位于路径段，不在 host**，因此所有正式插件的 origin 相同，浏览器天然的同源隔离不生效：

- `localStorage`、`sessionStorage`、`IndexedDB`、Cache API **在所有插件之间共享**
- 插件 B 一行 `localStorage.getItem(...)` 就能读到插件 A 存的内容，也能改、能删
- 前端开发者使用 `localStorage` 是本能行为，规范中目前也未禁止

代码库与文档中未出现过 `localStorage` / `IndexedDB` / `sessionStorage`，说明这一面尚未被纳入设计。

**修复方案（推荐组合）**：

1. **根本解 —— 每插件独立 origin**：把 id 从路径段移到 host 段，改为 `itplugin://<id>.localhost/<path>`。
   浏览器随即天然隔离所有 Web 存储。
   *需先验证*：Tauri 2 的 capability / CSP 配置对通配 host 的匹配方式，以及 `invoke` 在新 origin 下是否照常可用。调试协议同理处理。
2. **过渡与兜底 —— bridge 覆写**：在 `bridge.js` 注入时用按插件隔离的实现替换 `window.localStorage` 等。
   *注意此法不彻底*：同源 iframe 的 `contentWindow.localStorage` 仍是原生实现，可绕过覆写。
   所以它只能作为方案 1 落地前的过渡，或作为纵深防御的第二层，**不能单独使用**。
3. **规范层**：在插件开发规范中明确「插件数据一律用 `db` / `data` / `sqlite`，不要用 `localStorage` 等浏览器存储」，
   并说明原因。

#### 6.5.3 一旦授权即失效的能力（必须诚实告知用户）

有些能力在原理上就能绕过一切文件与数据隔离，**不能假装授权之后隔离依然成立**：

| 能力 | 为什么绕得过 |
|---|---|
| `exec` / `execStream` | 可执行任意程序，`cmd /c type <别的插件的数据文件>` 即可读取；隔离在文件层面完全失效 |
| L3 原生扩展（逃生舱） | 通用 fs 面，本就能读全盘 |
| `fs-named-path` 的 `appData` | 若解析结果覆盖到 iTools 自己的数据根，等于开放 `plugin-data/` |
| `process-manage` | 可读取其它进程信息 |

**对应措施**：

1. **数据根硬黑名单**：iTools 的数据根（含 `plugin-data/`、`dev/plugin-data/`）列入所有 fs 类 API 的**拒绝名单**——
   即便用户用 `pickDir` 亲自选中它，也一律拒绝。这条不接受例外。
2. **授权文案必须说实话**：`exec` 与原生扩展的授权提示要写明
   「授权后该插件可读取本机任意文件，**包括其它插件的数据和你的个人文件**」。
   按 `开发准则.md` 的诚信红线，不得用「仅执行程序」这类避重就轻的措辞掩盖真实影响面。
3. **这类能力一律 L3**：强人工审 + 每会话确认 + 审计日志。

#### 6.5.4 公共数据机制

跨插件协作的正当需求存在（词库、常用路径、统一配置等），但必须是**拥有者主动公开**，不是默认可读。

**模型：发布 / 订阅，只读公开，写权归拥有者。**

1. **默认全私有** —— 不声明就是任何插件都读不到。
2. **拥有者显式发布**：`plugin.json` 声明公开的命名空间

   ```json
   { "publicData": ["dict/", "presets/"] }
   ```

   只有列出的前缀对外可读，其余仍私有。

3. **读方 API 与权限**：

   ```js
   await itools.shared.get(pluginId, key)      // 只读
   await itools.shared.keys(pluginId, prefix)
   ```

   读方需声明 `read-shared` 权限，用户在管理中心看到的是「该插件会读取其它插件公开的数据」。

4. **写权限永远只归拥有者** —— 不提供 `shared.set`。任何插件都不能改别人的数据，公开的也不行。
5. **不做全局公共读写区** —— 一个所有插件可写的公共命名空间会变成污染与篡改的温床。
   有双向协作需求的走 `plugin-ipc`（域 10 的插件间能力调用）：A 请求 B 做一件事，**由 B 决定给什么**，
   这比暴露数据面安全得多，应作为主推方案。
6. **用户可见**：管理中心为每个插件展示「公开了哪些数据」与「读取了哪些插件的公开数据」，可随时关闭 `read-shared`。

#### 6.5.5 新增能力的隔离审查清单

按 `开发准则.md` 的强制审查机制，每新增一项 API，发布前逐条核对：

- [ ] 该 API 的作用范围是否由**后端**按 `caller_session` 判定，而非信任前端传入的插件 id？
- [ ] 传入的路径 / key / 标识符能否构造出指向别的插件的值（`..`、绝对路径、`../<其它 id>`、通配符）？
- [ ] 返回的数据里是否夹带了其它插件的信息（列表类 API 尤其容易漏，如进程列表、窗口列表、文件枚举）？
- [ ] 是否新增了浏览器级共享面（Web 存储、`BroadcastChannel`、`SharedWorker`、`window.name`、同源 iframe）？
- [ ] 调试会话与同名正式插件是否已按**完整会话身份**（id + dev 标志）区分，而不是只比 id？
- [ ] 若该能力在原理上绕得过隔离（见 6.5.3），是否已定为 L3 并在授权文案里如实说明？

## 八、与 uTools 的取舍对照

### 8.1 借鉴的（本文档已纳入）

子输入框 · 上下文感知（浏览器 URL / 文件管理器路径 / `window` 类型 cmds）· ubrowser 式自动化浏览器 · 搜索结果注入 · 动态指令 · 输入注入的完整形态（`typeString` + `paste*`）· FFmpeg 的交付形态（不内置、首次引导下载、进度回调、`kill`/`quit`）· `getFileIcon` · `startDrag` · `redirect` · 独立窗口与分离 · 取色器 · `desktopCaptureSources` · DIP 坐标转换 · 加密存储 · 附件存储 · 同步变更事件 · MCP tool 注册（含「不要写在进入事件里」的结论）

### 8.2 明确不抄的

| uTools 做法 | 不抄的理由 |
|---|---|
| preload 全开放 | Tauri 无 Node.js，工程不成立；且 all-or-nothing 是安全模型降级。改为白名单 + 受控逃生舱 |
| `db.put/get` 的 PouchDB 风格（`_rev` 冲突、`bulkDocs`、`allDocs`） | 对小工具作者是心智负担。iTools 现有 `db` / `data` 的 KV 更友好，**缺的是 SQLite** 而不是 rev 模型 |
| 插件包内携带 npm 包源码 | 与现有分发校验（32 MB / 4000 条目 / 禁二进制）冲突，且审核面爆炸 |
| 全局原始按键流 | 与键盘记录器无法区分，正当需求已被热键覆盖 |
| **平台托管的 AI 能力**（`utools.ai` / `allAiModels` 式的统一 LLM 网关） | **iTools 本身不包含 AI。** 插件需要大模型时，由开发者自行在插件里调用（`network` 权限 + `itools.fetch`），宿主不代理、不保管 key、不提供模型列表。<br>此项已评估并明确排除，请勿再次提议 |
| **付费 / 变现 API**（`isPurchasedUser` / `openPurchase` / `openPayment` / `fetchUserPayments`） | **产品定位是免费工具**，不做插件内购与分成体系。相应地也不需要开发者中心商品管理、服务端订单与回调、分成结算这一整套。<br>此项已评估并明确排除，请勿再次提议 |

### 8.3 iTools 已领先、需保住的

- **内置 OCR** —— uTools API 列表中没有
- **贴图 pin**
- **细粒度权限 + 运行时可撤销** —— uTools 是 preload 一把梭
- **宿主自身即 MCP server**（`src-tauri/src/mcp/tools.rs`、`ai_clients_status`）
  uTools 是「插件注册 tool 给它自家 AI Agent」；iTools 是「整个 iTools 能被 Claude Code 等**外部** agent 调用」。
  沿着这条往前走：**插件能力自动成为外部 AI 的工具** —— 这是别家给不了的差异化，值得作为长期主线。
- **Tauri 的体积与内存优势**

## 九、待决问题

1. **逃生舱的原生接口形态** —— 内嵌 JS 运行时 vs Rust 侧通用 API 暴露（倾向后者，见 5.4）。
2. **审核能力的规模化** —— 能力开放后审核工作量非线性增长。需要：静态检查工具链、能力组合风险自动标记、模型初筛 + 人工终审的分流机制。
3. **跨平台** —— 本文档大量能力基于 Win32 / `windows` crate。macOS / Linux 支持范围需单独规划，API 设计时应预留（如 `itools.platform` 已有的能力探测模式，建议扩展为 `itools.can("camera")` 之类的能力查询）。
4. **API 稳定性承诺** —— 何时把 `experimental` 转 `stable`，转正后的兼容承诺期多长。
