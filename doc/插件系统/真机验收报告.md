## 二、验收方法

没有靠人工点界面，而是写了一个自检插件 `tools/apitest`：

> ⚠ **它不在 `plugins/` 下，是有意的**：`tauri.conf.json` 的 `bundle.resources` 把 `../plugins`
> **整个打进安装包**并在用户首次启动时播种。而这个插件声明了全部 20 项高危权限、还带
> `background` + `mainPush`（随 iTools 启动自动后台跑）——放进 `plugins/` 等于把一个全权限、
> 开机自跑的插件发给每一位用户。发布前审查时发现它当时正躺在 `plugins/` 里，已挪到 `tools/`。


1. 它在 `plugin.json` 里声明全部 20 项权限，并声明 `background` + `mainPush`；
2. 由于声明了 `mainPush`，宿主会**自动后台常驻**它——于是 iTools 一启动，自检就自动跑起来，全程无需人工干预；
3. 插件逐项调用真实 API，每项独立超时、独立断言，失败不影响后续项；
4. 结果写进插件沙盒 `result.json`，由外部读取比对。

**唯一需要人工介入的 `fs.pickDir` 也做成了自动化**：插件把对话框标题设为固定串 `APITEST-PICKDIR`，外部一个 PowerShell 脚本轮询 `AppActivate` 等它出现，然后 SendKeys 填路径回车。这样 `fs.*` 全链路与 `serve` 也进了自动批。

> ⚠ **这个办法有个当时没发现的缺陷**：焦点其实落在文件列表上，键入变成了增量搜索，
> 回车确认的是列表里当时高亮的那一项——**它选中的并不是脚本指定的目录**。
> 详见第十节第 7 条（含两次修复尝试与实测结果）。对 `fs.*` 的验收结论没有影响（整条链路照样走通了），
> 但它确实往一个不相干的真实目录里写了文件。

这套办法的好处是**可重复**：改代码 → 重编 → 重启 → 读结果，一轮闭环约两分钟。本次前后跑了 **20 轮**。

权限通过直接写 debug 数据库的 `app_kv.settings` 预授权（debug 与 release 数据物理隔离，不影响正式版）。

> 复现方式：在 `%LOCALAPPDATA%\itools-dev\itools.db` 的 `settings` 里给 `apitest` 加回
> `plugin_permissions` 并从 `disabled_plugins` 移除，然后启动 debug 版即可。
> **验收结束后已撤销该插件的全部授权并将其禁用**——它拥有全量高危权限，不该常驻在任何人的环境里。

## 三、真机挖出并已修复的 9 个缺陷

共同点：**编译器和单测都发现不了**，只有真跑才暴露。

### 1. 托盘状态未注册 —— 功能 100% 不可用

- 现象：`state not managed for field 'state' on command 'plugin_tray_set'`
- 原因：`lib.rs` 漏了 `.manage(TrayState::default())`
- 修复：补上注册。这类漏注册编译期毫无提示，一跑就炸

### 2. `proc.kill` 只保护当前进程，杀得掉另一个 iTools 实例

- 现象：自检里「kill 自身应被拒」返回「未被拒绝」——**实际杀掉了正在运行的正式版 iTools**
- 原因：自保护只比对 `GetCurrentProcessId()` 与父进程链。机器上同时跑着正式版和 debug 版时，另一个实例「确实不是自己」，于是放行
- 影响：用户视角就是「装了个插件，我的 iTools 被关掉了」
- 修复：改为按可执行文件名保护**所有同名实例**

### 3. `sys.getPath` 返回值格式不一致

- 现象：`getPath("temp")` → `...\Temp\`（**带尾反斜杠**），`getPath("downloads")` → `...\Downloads`（不带）
- 原因：`std::env::temp_dir()` 与 `dirs::download_dir()` 对尾部分隔符的约定不同
- 影响：插件拼路径必踩——`getPath("temp") + "\\x.txt"` 拼出 `...\Temp\\x.txt`。验收时我自己第一个踩到
- 修复：新增 `normalize_dir` 统一去尾（盘符根 `C:\` 例外保留），`sys.getPath` 与 `paths.resolve` 共用

### 4. 回收站完全不工作 —— 本轮最难定位的一个

- 现象：`trash()` 返回成功，但文件**还在原处**
- 排查过程（先后换了五种实现，全部失败）：

  | 实现 | 报错 |
  |---|---|
  | `IFileOperation`（原始实现） | `SHCreateItemFromParsingName` → `E_INVALIDARG (0x80070057)` |
  | 老 API `SHFileOperationW` | `124 (DE_INVALIDFILES)` |
  | 裸 `PCWSTR` 取代 `HSTRING` | 同样 `E_INVALIDARG` |
  | 专用 STA 线程（排除 apartment 因素） | 同样 `E_INVALIDARG` |
  | PowerShell + `VisualBasic.FileIO` 回退 | 「不支持给定路径的格式」 |

- **真正的根因**：`std::fs::canonicalize` 在 Windows 上返回**扩展长度路径** `\\?\C:\...`。这个前缀对 Win32 文件 API 合法，但 **shell 层与 .NET 都不认**。五种实现收到的是同一个带前缀的路径，所以全都断在同一处
  > 破案线索是错误信息里那句「路径 68 字符」——实际路径只有 64 字符，多出来的 4 个正是 `\\?\`
- 修复：新增 `strip_extended_prefix`，在**真正调用 shell 之前**摘掉前缀（校验逻辑仍必须用 canonicalize 解析符号链接、防绕过）
- 验证：文件从原位消失，且**确认真的在回收站里可还原**（`Shell.Application` NameSpace(10) 查到了探测文件）

### 5. 摄像头对绝大多数 USB 设备不可用

- 现象：`camera.grab` 报「设置摄像头输出格式失败……该媒体类型不受支持」
- 原因：创建 Source Reader 时第二参传 `None`，没启用 `MF_SOURCE_READER_ENABLE_ADVANCED_VIDEO_PROCESSING`；代码直接请求 `MFVideoFormat_RGB32`，而**罗技 C930c 这类常见 USB 摄像头原生只输出 MJPG / YUY2 / NV12**
- 影响：设备枚举正常但**取帧对绝大多数 USB 摄像头都失败**——「看得见、用不了」
- 修复：启用高级视频处理，由 Media Foundation 自动插入颜色转换 MFT；另补了「指定分辨率不被支持时退化为设备默认分辨率」
- 验证：拿到真实 640×480 PNG（325 KB）

### 6. 预览流一启动就自己结束

- 现象：`streamStart` 返回了 id，几秒后 `streamStop` 报「该预览流不存在或已结束」，`frames` 恒为 0
- 原因：`ReadSample` 返回**空样本但不报错**是 Media Foundation 的正常行为（设备刚启动、流控打 stream tick 时都会），含义是「此刻无数据，继续读」。实现把第一次空样本当成了流结束
- 影响：**预览流完全不可用**。而单帧 `grab` 因为恰好赶上设备就绪反而是好的——表现成「拍照能用、预览不能用」这种很难联想到根因的样子
- 修复：空样本改为重试（最多 60 轮 × 20 ms），只有真正的 `ENDOFSTREAM` 或错误才结束
- 验证：3 秒内稳定收到 **12 帧**

### 7. 进度推送把大文件下载拖慢（缺陷属实，但当时的归因只对了一半）

> ⚠ **本条已被第二轮复验部分推翻，以第十节为准。**原文把「比 curl 慢 93 倍」整个记在进度推送头上，
> 而那个 curl 对照是**经本机代理**测的、iTools 走的是**直连**——两条链路差 400 倍，对照本身不成立。
> 节流失效是真的、修复也是真的，但它解释不了当时看到的全部差距。下面保留原始观测，只更正归因。

- 现象：`runtime.ensure("ffmpeg")`（160 MB）跑满 15 分钟未完成
- ~~对照：同机 `curl` 下载**同一 URL 只要 10.85 秒**（15.4 MB/s）~~ ← **无效对照**，见第十节
- 定位：在插件侧累计进度事件测速，得到真实速率 **166 KB/s**，且 90 秒里推了 **430 次**事件（约每 209 ms 一次）
- 原因：下载循环用的是**纯时间节流**（「距上次超过 150 ms 就推」）。而真机上 `webview.eval` 单次往返的开销**本身就大于 150 ms**，于是每个数据块回来时条件都已成立，节流完全失效，退化成「每块都推」
- 修复：改为**时间与字节数双条件**（至少 400 ms **且** 至少 4 MB）
- 验证：事件数 430 → **17**，速率 166 KB/s → **1.42 MB/s**（**8.5 倍**改善——这一条站得住；「93 倍」那个说法不成立）
- **同类缺陷一并修掉**：`net.rs` 的 `plugin_download` 也是纯 150 ms 时间节流，同样的坑，已改为「400 ms 且 2 MB」

### 8. `context.activeWindow` 拿不到时抛错而非返回 null

- 原因：实现用了 `.ok_or_else(...)`，而文档一直写的是「拿不到返回 null，必须判空」
- 影响：「此刻没有前台窗口」是完全正常的状态（刚启动、后台拉起、锁屏都会遇到）。当错误抛出等于逼每个插件 catch 一个不是错误的情况，漏 catch 还会中断整段初始化
- 修复：返回类型改为 `Option<ActiveWindowInfo>`

### 9. scope 路径把 `\\?\` 前缀暴露给插件

- 现象：`fs.pickDir` 返回的 `path` 是 `\\?\F:\ClaudeWorkspaces\...`
- 原因：与第 4 条同源——`canonicalize` 的扩展长度形式直接透给了插件
- 影响：插件把它显示给用户会看到莫名其妙的 `\\?\` 开头；再传给 `openPath` / `showItemInFolder` / 回收站这类 shell API 会直接失败
- 修复：对外暴露的 `path` 统一剥离前缀，内部校验仍用未剥离的形式
- 说明：**此项修复有单测覆盖（3 个），但真机复验时机器已锁屏，未能再跑一轮确认**

## 四、运行时清单：已钉版本并填入实算哈希

原先三个下载地址都是 rolling `latest`，哈希根本钉不住。现已全部换成不可变产物，且**每个哈希都是本机下载后自行计算**的：

| 运行时 | 版本 | 体积 | SHA-256 来源 |
|---|---|---|---|
| ffmpeg | `n8.1.2-34-g9b6c8969e0`（BtbN `autobuild-2026-07-31-14-10`） | 167,405,723 B | 本机实算，**与该 release 自带的 `checksums.sha256` 逐字符一致** |
| adb | `r37.0.1` | 8,044,989 B | 本机实算（Google 清单只声明 SHA-1；体积与清单一致可交叉印证） |
| yt-dlp | `2026.08.19` | 17,840,399 B | 本机实算 |

调研中发现的三个坑，已写进模块头文档：

1. **ffmpeg 不能钉日构建**：BtbN 只保留最近约两周的日构建 tag，更早的仅留每月最后一天的快照。钉日构建两周后就 404。现钉的是月末快照（按现行保留策略可存活约两年）。要真正长期可靠，应把该 zip 镜像到自己可控的存储
2. **adb 的 URL 后缀从 r36 起由 `-windows.zip` 改成了 `-win.zip`** —— 原先设想的 `platform-tools_r35.0.2-windows.zip` 那种模板实际 404。权威文件名来源是 `repository2-3.xml`
3. **adb.exe 不能单独抽出**，它依赖同目录的 `AdbWinApi.dll` / `AdbWinUsbApi.dll`

验证结果：

- `runtime.ensure("yt-dlp")` 真实走完「下载 → SHA-256 校验 → 落盘」，`installed: true`
- `runtime.exec("yt-dlp", ["--version"])` → **`2026.08.19`**，与钉的版本号完全一致
- `runtime.exec("ffmpeg", ["-version"])` → **`ffmpeg version n8.1.2-34-g9b6c8969e0-20260731`**，同样完全一致

## 十、第二轮：遗留事项收尾，以及由此挖出的两个新缺陷

- 时间：2026-08-20 下午，**桌面处于解锁状态**
- 方式：同一套 `tools/apitest` 自检，重编 debug 后重跑（`cargo check` 零警告 → 单测全绿 → 重启读结果）
- 结果：**92 项 PASS 87 / FAIL 1 / SKIP 4**；唯一那个失败是环境条件，不是缺陷（见第 6 条）

### 1. 遗留第 2 项结案：scope 路径前缀 —— 真机复验通过 ✅

`fs.pickDir` 真机返回：

```json
{ "id": "f133d52d…", "path": "F:\ClaudeWorkspaces\iTools-plugins\deskbox", "noExtendedPrefix": true }
```

不再带 `\?\` 前缀。同时**把这条断言固化进了自检**——原来只断言 `path` 非空，那种断言即使前缀回来了也照样绿。
现在自检里显式检查 `path.indexOf("\?\") !== 0`，退化会被当场拦住。

### 2. 遗留第 3 项结案：回收站原生实现已恢复 ✅

原来「走原生还是走 PowerShell 回退」从返回值上**完全看不出来**——两条路都只回一个 `ok: true`。
所以先在 `trash_paths` 里补了一行日志把实际分支钉进 `itools.log`，然后真跑：

```
[15:04:37] [iTools][plugin] trash: 请求 1 条，原生 IFileOperation 成功 1 条，未触发回退
```

即：前缀问题修好后原生这条路**确实恢复了**，PowerShell 回退退回到纯兜底位置，不再是常态路径。
这行日志值得长期留着——否则哪天原生又悄悄坏了，回退会把它兜住，表现成「功能正常，只是每次删除都多起一个进程」，没人会发现。

### 3. 遗留第 1 项：**原结论被推翻**，真凶不是 debug 构建 ❌

原报告推断「剩余速度差距来自 debug 未优化（逐块 SHA-256 与 rustls 解密）」。
为此写了 `src-tauri/examples/dl_bench.rs`——把 `download_and_verify` 的核心循环原样搬出来
（同一个 ureq 配置、64 KB 分块、逐块 SHA-256），debug / release 各跑同一个 URL 做 A/B。

**第一次跑就翻车了**：debug 下 6 分钟只下了 28 MB 然后**内存占用一个字节都不再增长**——不是慢，是**卡死**。
release 同样卡在 17 MB。而同一时刻用 curl 拉同一个 URL，**6.89 秒下完整个 167 MB**。

顺着这个矛盾查下去，发现了一个关键事实：**这台机器上 `all_proxy=http://127.0.0.1:7897`、系统代理也开着，
所以 curl 默认走代理；而 iTools 设置里代理是关的、`direct_agent()` 又显式 `try_proxy_from_env(false)`，走的是直连。**
两者根本不是同一条链路。同一 URL、同一时刻实测：

| 链路 | 速率 |
|---|---|
| curl **经代理** | 167 MB / 7.49 s = **22.3 MB/s** |
| curl **直连**（`--noproxy '*'`） | 25 s 只下了 1.41 MB = **56 KB/s** |

**所以第八节第 1 条与第三节第 7 条里那个「curl 15.4 MB/s」的对照是无效的**——它测的是代理链路，
iTools 测的是直连链路，把两个数相减得到的是链路差，不是构建类型差。

把 debug / release 放到**同一条健康链路**（都经代理）上重测，构建类型的真实影响才浮出来：

| 同一条链路、同一个 167 MB 文件 | debug | release |
|---|---|---|
| 整体吞吐 | **21.88 MB/s** | **28.44 MB/s** |
| 其中 read（网络 + TLS 解密） | 5.388 s | 5.349 s |
| 其中 hash（逐块 SHA-256） | 1.837 s | 0.189 s |
| 纯哈希吞吐（同一份数据一次性算） | 89 MB/s | 883 MB/s |

结论：
- **debug 下 SHA-256 确实慢约 10 倍**（89 vs 883 MB/s）——这一半的猜测是对的；
- 但 89 MB/s 远高于任何真实网速，**它根本不是瓶颈**（只占 7.3 s 里的 1.8 s）；
- TLS 解密两边几乎一样（5.39 vs 5.35 s）——ring 用的是手写汇编，不随 `opt-level` 变化，这一半的猜测是错的；
- **debug 构建在健康链路上就能跑到 21.9 MB/s**，所谓「debug 太慢」根本不存在。

两次下载算出的 sha256 都与清单里钉的值逐字符一致，顺带又交叉印证了一次清单哈希。

### 4. 新缺陷 A：出站请求**没有读超时**，链路僵死就永久挂起（已修）

上面那个「卡死 6 分钟纹丝不动」不是偶发，是必然会发生的事：`ureq 2.12.1` 的默认值是
`timeout_connect: Some(30s)`、**`timeout_read: None`、`timeout_write: None`** ——
「连不上」会超时，「连上之后对端不再发数据」**永远不会**超时。而 `http.rs` 的两个 Agent 都没设。

对用户来说这就是「点了安装 → 进度条停住 → 永远不结束、也永远不报错」，比直接失败更糟：没有任何信号提示该重试。
这多半也是第一轮那句「`runtime.ensure(ffmpeg)` 跑满 15 分钟未完成」的真正成因。

- 修复：直连与代理**两个** Agent 都加上 60 秒**空闲**超时（不是整体超时——大文件在慢网络上正常也要跑很久，
  给整体设上限必然误杀；而「连续 60 秒一个字节都没有」无论多慢都只能是死了）。
- 调用点自己设的 `.timeout()`（更新下载 600s、镜像竞速 5s）在 ureq 里优先级更高，既有语义原样不变。
- 配了测试：断言两个 Agent 的 Debug 输出里真的带着这个配置，而不只是「代码里写了一行」。

### 5. 新缺陷 B：代理关闭时不走 GitHub 镜像（按海风哥要求已实现）

直连 GitHub 56 KB/s 且会僵死，这在国内是常态。而项目里**本来就有**一套成熟的 GitHub 镜像机制
（`plugin/mirror.rs`，内置 gh-proxy.com / ghfast.top / ghproxy.net），却只用在插件包下载上，
宿主托管的运行时下载完全没用上。

实测三家镜像对 **release 资产**（不是插件归档）在直连下的表现：

| 源 | HTTP | 12 秒内下载量 | 速率 |
|---|---|---|---|
| **gh-proxy.com** | 200 | 13.77 MB | **1.15 MB/s** |
| ghfast.top | 200 | 0.93 MB | 78 KB/s |
| ghproxy.net | 200 | 0.76 MB | 63 KB/s |
| github.com 直连 | 200 | 1.41 MB | 56 KB/s |

实现要点：

- **顺序按有没有可用出口来定**：配了代理 → 官方优先、镜像兜底；没配代理 → **镜像优先、官方兜底**
  （把官方排前面只会让没代理的用户白等几十分钟）。
- 用户显式选了「只走官方」（`plugin_mirror_mode = official`）时**一个镜像都不用**——那是他划下的信任边界。
- **镜像前缀是从已配置的 `archive` 模板里现场切出来的，不是写死 `https://{host}/`**：
  服务端下发的镜像若用别的形态（如 codeload），切不出前缀就跳过它，绝不拿一个猜出来的地址去下可执行文件。
- **为什么这里敢用第三方镜像**：运行时清单每一项都带本机实算的 sha256，下载完必须逐字节校验，
  不匹配直接丢弃且**从不落盘**。镜像最多能让下载失败，改不动落地的内容。
  哈希不符时**不换源重试**——那说明内容确实不对，换个源再下既不会让它变对，还会把投毒掩盖成「网络问题」。
- 配了 8 条测试（顺序、模式、非 GitHub 地址、模板推导、不健康条目过滤、清单哈希闸门）。

**端到端真机验证**（把已装的 `host-runtimes/` 整体改名挪走，让它在「iTools 代理关闭」的真实状态下重下一遍）：

```
[15:04:44] runtime yt-dlp: 尝试源 1/4 = gh-proxy.com
[15:05:26] runtime yt-dlp: 下载完成，来源 gh-proxy.com，17840399 字节
[15:05:27] runtime ffmpeg: 尝试源 1/4 = gh-proxy.com
[15:11:01] runtime ffmpeg: 下载完成，来源 gh-proxy.com，167405723 字节
[15:11:07] runtime_ensure 完成: runtime=ffmpeg
```

- 「尝试源 1/4」= 3 个镜像 + 官方兜底，代理关闭所以镜像排在前面——**顺序按设计生效**。
- 两个包都**首个源就成功**，SHA-256 校验通过并落盘；`ffmpeg -version` / `yt-dlp --version` 输出与清单里钉的版本逐字符一致。
- ffmpeg 实测 **167,405,723 字节 / 334.8 秒 = 500 KB/s**。比直连的 56 KB/s 快约 9 倍——但更关键的是**它跑完了**，
  而不是像直连那样下到 17~28 MB 就僵死。
- 随后用**刚下下来的这个 ffmpeg** 录了 mp4，再用同来源的 ffprobe 验：`h264 / 2560×1440 / 40 帧 / 4.000 秒`
  （录制参数正是「4 秒 @ 10fps」）——「镜像下载 → 校验 → 解压 → 真的能用」整条链闭合。

**顺带把进度节流也在一次真实的大文件下载上复验了**（第一轮修完后一直没机会重跑，因为运行时已经装好了）：
167 MB 下载共推 **41 次**进度事件 = **每 4 MB 一次**，与 `PROGRESS_MIN_BYTES = 4 MB` 的设计完全吻合
（第一轮坏掉时是 90 秒推 430 次）。节流这一条实锤有效。

> **更新包（updater）没有一并接上，这是有意的**：更新包下下来是**直接执行**的，而它当前的信任模型
> 就是「URL 主机必须是 github.com」——既没有 sha256 也没有签名校验（只验了是不是 PE 文件）。
> 让它走第三方反代 = 任何一个镜像都能给用户塞一个任意安装包并被执行。要加速更新，**前提是先给发布产物加可信哈希或签名**。

## 十一、更新器：先加哈希校验，再接镜像

第十节第 5 条里刻意没动更新器，理由是它的信任模型撑不住镜像。海风哥定的方案是「**先加哈希校验，再接镜像**」，本轮已落地。

### 为什么必须是这个顺序

更新包下下来是**直接执行**的（`launch_installer_and_quit`），而它此前的全部信任都压在
`ensure_channel_url` 那一句「URL 主机必须是 github.com」上——既没有 SHA-256 也没有签名，
只验了文件是不是 PE。在这个前提下让下载走任何第三方反代，等于允许对方给用户塞一个任意安装包并被执行。

### 客户端改动

1. **可信哈希从哪来**：`<官方安装包 URL>.sha256`（`updater.rs` 的 `INSTALLER_HASH_SUFFIX`）。
   不新增任何契约字段——地址由官方 URL 现场推导，`UpdateInfo` / `types.ts` / `contract-snapshot.json` 一个字没动。
2. **哈希只从官方源直连取，绝不经镜像**。这是整套设计的支点：镜像若能同时替换包和哈希，校验就是自欺欺人。
   哈希文件只有几十字节，直连再慢也是一次可以忍受的小请求。
3. **没有可信哈希就只走官方源**（`candidate_sources` 的 `None` 分支）。
4. 有哈希时才按第十节那套顺序取候选（无代理→镜像优先、有代理→官方优先、用户选 `official` →一个镜像都不给）。
5. 下载改为**边写边算 SHA-256**，逐项校验：体积 → 哈希 → PE。**哈希不符不换源重试**——
   那说明内容确实不是官方那一个，换个源再下既不会让它变对，还会把「某个源在投毒」掩盖成「网络问题」。

### 发布流水线改动

- `.github/workflows/release.yml`：新增「生成并上传安装包 SHA-256」，产出 `<安装包文件名>.sha256`，
  **排在「转为正式发布」之前**（release 一转正式客户端就可能看到它，那时哈希必须已在位）。
- `scripts/publish.sh`（官网线）：同样产出并上传哈希，含固定名副本 `iTools-latest-setup.exe.sha256`。
  官网线没有镜像，但这道校验照样能挡住传输损坏、中间人替换、以及「服务器上那份被人动过」。
  服务端 `/download` 是普通 `ServeDir`、不限扩展名，`.sha256` 不需要额外改动就能取到。

### 验证到了哪一步（如实标注）

- ✅ **优雅退化已用真实 release 验证**：当前 `v1.5.6` 的附件只有安装包一个，
  探测 `…/iTools_1.5.6_x64-setup.exe.sha256` 返回 **HTTP 404** → 走 `None` 分支 → 只用官方源，
  行为与改动前逐字节一致。**已发布的版本不会因为这个改动出任何问题。**
- ✅ 单测覆盖：哈希文件解析的严格性（6 种非法输入全部拒绝）、以及**安全闸门**
  「没有可信哈希时候选源里绝不出现镜像」。
- ⚠ **「有哈希 + 走镜像」这条完整路径尚未真机跑通**——它要等下一个带 `.sha256` 附件的 release 发出来才能验。
  代码写完了、单测过了，但**不能说它已经真机验证过**。下次发版时应当专门盯一眼日志里的
  `下载更新包：尝试源 1/N = …` 与 `更新包下载完成，来源 …`。

## 十二、发布前审查：又挖出 3 个欺骗性桩（已修）

按 `doc/开发准则.md` 第二、三节，发布前做了一次**多视角并行 + 逐条对抗验证**的审查：
6 个独立视角（空桩/假返回、日志泄露、UI 全链路、安全红线、权限门禁、文档承诺 vs 实现）
各自扫一遍，报出的每一条再交给一个**专门去证伪它**的独立视角复核。共报 23 条，
证伪后确认 7 条（去重后 5 个问题），其余 16 条被驳回（多为「诚实占位」或误读）。

另有一道**确定性**交叉核对（不靠模型判断）：254 个 `#[tauri::command]` 的
「实现 + `lib.rs` 注册 + permission toml + capabilities + `bridge.js` 调用」五处闭环，
**零缺口**；明文凭据 / 个人数据 / 写死服务端地址扫描，**零命中**。

### 确认成立并已修的 5 条

| # | 位置 | 判定 | 问题 |
|---|---|---|---|
| 1 | `indicator.rs` | 欺骗性桩 | 托盘「⚠ XX 正在使用麦克风（点击停止）」**点了不生效**——`stop_all_sensitive` 只掐摄像头与 `record_av`，麦克风录音（`audio`）和 GIF 录屏（`record`）根本没有停止通路 |
| 2 | `indicator.rs` | 欺骗性桩 | `record_av::active_sessions()` 返回的是「`<id>` 正在`<label>`」这种**整句描述**，却被当成 `plugin_id` 用：托盘文案变成「apitest 正在录屏 正在使用录屏 / 录音」，且掐断时拿假 id 去 `same_as` 匹配**永远匹配不上**——连它自己也停不掉 |
| 3 | `input_api.rs` | 欺骗性桩 | 剪贴板监听把事件推给**写死的** `plugin` / `plugin-dev` 窗口。后台常驻插件跑在 `plugin-bg-<id>` 里，于是 `watchStart()` 返回成功、监听线程也真在跑，但 `onChange` **永远不触发**——而「常驻后台盯剪贴板」恰恰是这个能力最典型的用法 |
| 4 | `exec.rs` | 轻微（隐私红线） | `exec_stream` 把插件传进来的 `program` **原样**写进 `itools.log`。它可能是用户经 `fs.pickFile` 选出来的完整路径，带着用户名与私人目录结构，而 release 日志长期留存、报障时整份发出 |
| 5 | `window-itools-api.md` | 轻微 | 文档明确断言 `runtime.exec` 的返回结构**没有** `truncated` 字段，实现其实有——作者会因此漏检一个真实存在、且关系到「结果是否完整」的字段 |

修法：

1+2. `camera` / `record_av` / `audio` / `record` 四处统一改为传递**完整会话身份**（id + dev）而不是裸 id 或描述串；
   `audio` 与 `record` 各补一个 `force_stop()`；`stop_all_sensitive` 覆盖全部四类。
   顺带修掉一个连审查都没报的隐藏问题：原实现写死 `dev: false`，**调试会话的摄像头一样掐不掉**。
   并把 `record_av` 的用途标签用起来，托盘现在如实区分「内录」（算 `audio-capture`）与「录屏」（算 `screen-capture`），
   而不是笼统一句「录屏 / 录音」。
3. 事件改推回 `webview.label()`（发起调用的那个窗口本身）；删掉那个按会话推导固定 label 的函数——它就是病根。
   同时补上会话收尾钩子 `input_api::stop_all_for_session`，接进 `commands.rs` 与 `serve_api` / `camera` / `record_av`
   并列的两处——原注释写着「窗口关闭都能回收」，而实际上**一个清理调用都没有**，插件被禁用后轮询线程会一直跑下去。
4. 只记**末段**文件名。
5. 文档更正为「与 `itools.exec` 一样有 `truncated`」。

另修正一处夸大措辞：`serve_api` 的局域网准入 token 与 `fs_api::new_scope_id` 用的是同一套
（sha256(时间戳+计数器+PID+堆地址)），`fs_api` 如实标注了「不是密码学级随机数」，而 `serve_api`
的注释写的是「不可预测」。实际熵约 50~60 位、服务默认几十秒 TTL，在这个窗口内经网络暴力枚举不具现实可行性，
所以**本次不改实现**，但把注释改成事实，并写明「要把 `serve` 做成长时间常开的服务，必须先换成
